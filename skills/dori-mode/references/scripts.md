# Scripts

`scripts/` is a bun + TypeScript package with one CLI, `dori`. Every external command runs as an argv array; nothing builds a shell string.

## Install and test

Installing, testing, requirements and the library modules are in [development.md](development.md).

Hooks are argv templates for your messenger CLI. `{thread}`, `{text}` and `{key}` are filled into each argument separately, so the text stays one argument whatever it contains.

dori has no task-tracker integration: it knows lanes, PRs and threads only. Keeping a tracker in step with lanes is the lead's job through the tracker's own tools (an MCP like any other). Tracker keys left in a config or lane file written for an older version are ignored.

### Always-on behavior

These used to be boolean config flags; they are always on now. A config that still carries one of the old keys (`sweepSnapshot`, `sweepTask`, `superviseTasks`, `operations`, `threadArchive`, `ciFollowUp`, `claimDelivery`, `branchCleanup`, `eventSources`, `schedules`, `laneReports`) loads as before: the key is ignored and named once on stderr as `CONFIG_FLAGS_REMOVED <keys> in <path>`, so it can be deleted at leisure. The removed `hooks.threadDone` hook works the same way: an old config's `hooks.threadDone` is ignored with one `CONFIG_HOOK_KEYS_REMOVED` warning.

- **Sweep snapshot** (`supervise`): each 30 s sweep round takes one `herdr pane list` per machine, shared by watch, guard, dead-panes, recover and freshness; screen and process reads are reused while a pane's herdr `revision` is unchanged, and the reads of changed lanes run at most 4 at a time per machine.
- **Supervisor tasks** (`supervise`): there is no single loop but four independent tasks: `inbound` (Discord catch-up and the gateway heartbeat), `delivery` (owner delay, ack and unhandled notices, then lead delivery), `sweeps` (the 30 s sweep round) and `polling` (waits, GitHub, event sources and lane reports), so inbound, owner notices and lead delivery never wait behind a slow sweep. Every sweep is tracked by the watchdog. A task whose pass runs past 5 min is reported by name as `TASK_STALLED <task>` (logged and queued for the lead; a stalled `delivery` also posts one line to the first `discordChannels` entry) while the other three keep working, and `TASK_RECOVERED <task>` is logged when it moves again; past 15 min it withholds `WATCHDOG=1` as `task:<task>`, so systemd restarts the supervisor. Each task's first pass is logged as `STARTUP_TIMINGS first-<task>` (`first-sweep` for the sweeps).
- **Operations** (`close`, `watch`, `supervise`): every effect of a close (worktree removal, branch deletes, tab or pane close) is an operation row (`operations.json`; on the sqlite store the `operations` table of `supervisor.sqlite`), written durably as attempted before the effect and settled by a read-back after it. An interrupted close is resumed by the next watcher pass without repeating an effect, or stops as urgent `OPERATION_AMBIGUOUS`; see `dori close` and `dori ops`.
- **Thread left open** (`close`, `watch`, `supervise`): no close path archives the lane's Discord thread, shared or not. The thread stays open for the lead's outcome report, and the owner closes it with the **스레드 닫기** button, which `dori supervise` posts once the thread's work is finished and reported (or a `dori reported --final` post carries).
- **CI follow-up** (`supervise`): after each GitHub poll, every open PR of an open lane (its `Done =` names the PR, or a lane worktree has its branch) is followed, only when its head branch lives in the PR's own repository: a fork PR (or one whose head repo GitHub does not report) belongs to no lane, whatever its number or branch name, so it gets no CI message, merge, merge lane or issue close. Failing checks at the head SHA queue one lane message with an ID (`ci-<repo>-<n>-<sha7>`; `lane-messages.json`, on the sqlite store the `lane_messages` table), typed once (send-text, one Enter) only while the lane's pane exists, runs an agent, is idle and the lane is not paused; the lane confirms with `dori report ack <id>`. A message still queued (busy, paused, missing pane) or delivered without an ack `ciConfirmMin` after it was queued is one urgent `LANE_MESSAGE_UNCONFIRMED`. A green PR is read again (`gh pr view`) and merged only when its lane's done claim (`dori claim-done` or a remote `done` report) recorded this PR at exactly its current head SHA (the claim reads the lane's open same-repo PRs live from GitHub and stores `claim.pulls`; a push after the claim, or a claim without them, never auto-merges), and it is open, from a branch of its own repo, into `ciMergeBase`, never into `main`, still at the polled head, not a draft, every check green with at least one passed (no checks, or only skipped or neutral ones, is never green) and GitHub says MERGEABLE and CLEAN: `gh pr merge <n> --merge --match-head-commit <sha>`, never `--admin`, then urgent `CI_MERGED ... merge=<sha>`. A conflicting PR whose own lane is live (not paused, its pane exists and runs an agent, busy or idle; an unreadable pane list counts as live) gets one lane message asking it to rebase onto `ciMergeBase` itself (`rebase-<repo>-<n>-<sha7>`, delivered and confirmed like the CI message, superseded once the PR stops conflicting at that head) and no merge lane. Once that lane is paused, closed or dead (no pane, pane missing, no agent in it), the PR gets a merge lane (`merge-<repo>-<n>`, a detached worktree of the PR branch under `worktreeRoot`, fetched as `git fetch --end-of-options origin +refs/heads/<b>:refs/remotes/origin/<b>` after the branch name passes `git check-ref-format --branch` and does not start with `-`, the same thread, `Done = merged <repo>#<n>`) that resolves, waits for green and merges; when the host guard holds or the launch fails, urgent `CI_CONFLICT`. Merges and launches are operations (`<lane>/merge/<repo>#<n>@<sha>`, `<lane>/merge-lane/...`), so a restart never repeats one; a merge GitHub refuses 3 times is urgent `OPERATION_FAILED`. `GH_PR * checks_failing` and `GH_PR * conflicting` are digest unless `eventPolicy` names them. Lanes still wait on their own CI.
- **Merge read-back** (`supervise`): after each GitHub poll, every merged PR of an open lane that the supervisor did not merge itself (its own merges are read back as `CI_MERGED`) is read once with `gh pr view` (a `<key>/merge-verify/<repo>#<n>` operation): digest `MERGE_VERIFIED <repo>#<n> into <base> lane=<key> merge=<sha> <url>`, or urgent `MERGE_UNVERIFIED` when GitHub does not report it merged with a merge commit or the read fails 3 polls in a row. A done-claimed lane whose PR is merged then closes on the watcher's next pass (Claim delivery below), with its worktree and branch (Branch cleanup). The `GH_PR ... merged` line itself is digest.
- **Issue close** (`launch`, `adopt`, `supervise`): a brief line `issue: owner/repo#N` (a line of its own, optionally a list item) binds the lane to that GitHub issue (the `ghIssue` registry field); a malformed value refuses the launch. While the lane's PR is open, CI follow-up plans a `<key>/close-issue/<issue>@<repo>#<n>` operation, so the issue is still closed when the lane closes before the merge. Once a poll sees that PR merged and `gh pr view` confirms it MERGED into `ciMergeBase`, dori runs `gh issue close <N> --comment "Closed by dori: <repo>#<n> (lane <key>) is merged into <base> as <sha>. <url>"` once (read back with `gh issue view`) and logs digest `CI_ISSUE_CLOSED`. An issue already closed is verified without a comment; a PR merged into another base never closes it; a close GitHub refuses 3 times is urgent `OPERATION_FAILED`.
- **Claim delivery** (`watch`, `supervise`): a done claim is the supervisor's to settle. `LANE_DONE_CLAIMED` is urgent by default and wakes the lead, the claim's `closeAfterMin` window starts when the claim reaches the lead, not at the claim, and at its end the live re-check closes the lane or objects (urgent `LANE_NOT_DONE`); a merged PR closes it at once. A close after the claim reached the lead is `LANE_CLOSED <key> closed seen-claim` (digest: the lead already heard of it); a close before that (a merged PR) is plain urgent `LANE_CLOSED`. With `eventPolicy` making `LANE_DONE_CLAIMED` `lead-digest`, the window instead starts when the watcher hands the claim over. The watcher enqueues the claim as `done-claim:<key>:<claim time>` and records `claim.deliveredAt` on the first pass that reads it delivered: logged to a warm lead, or in a cold start that has confirmed (a batch logged for a cold start that has not confirmed does not count). Until then the claim waits, however late. `dori watch`, with no supervisor, counts printing the line as delivery; a claim announced by an older dori (no event id) keeps its window from the claim. A lane whose brief declares `autoClose: machine` claims as `LANE_AUTO_CLAIMED` (digest) and closes as `LANE_AUTO_CLOSED` (urgent), with the window from the claim, so the claim needs no lead wake (objections stay urgent `LANE_NOT_DONE`).
- **Branch cleanup** (`close`, `watch`, `supervise`): SHA-bound branch cleanup (design 4.3). For each `merged <owner/repo>#N` Done signal the close reads the PR's head branch, head SHA and base (`gh pr view`), and for each lane worktree (the lane's own cwd included when it is a linked worktree) it looks up a PR merged from that worktree's branch into `ciMergeBase` (`gh pr list --state merged --head <b>`), so no special Done line is needed; a worktree on that branch is removed only while its HEAD is exactly the merged head, otherwise it stays (`branch-bound worktree <wt> kept: ...`, never swept). After the worktrees it re-reads the local ref, the worktree list and the remote ref, and deletes the local branch with a compare-and-delete (`git update-ref -d refs/heads/<b> <sha>`) only when the local ref and the remote ref (if it still exists) still point at the merged head and the branch is not checked out, not protected (`main`, `master`, `dev`, `develop`, `trunk`, `release`, `staging`, `production` or the PR's base) and not named by another open lane's Done line. Anything else keeps the branch with one receipt line, `branch <b> kept: <why>` (a commit after the merge names both SHAs). Each delete is a `<key>/branch-delete/<owner/repo>#N@<sha>` row, planned with its git dir before any worktree goes, so an interrupted close resumes it. Before the local branch, the remote branch is deleted under the same rules with a lease on the merged head (`git push --force-with-lease=refs/heads/<b>:<sha> <remote> :refs/heads/<b>`, a `remote-branch-delete` row); one already gone is skipped. A lane cwd is removed only at exactly a merged head; dirty, it is kept. A done-claimed lane whose PR is confirmed merged (a verified `merge` operation of the lane, i.e. CI_MERGED; a `merged` Done signal reading MERGED; or a PR merged into `ciMergeBase` from a lane worktree's branch at its HEAD) closes on the next watcher pass instead of waiting out the claim window. Remote lanes are skipped.
- **Event sources** (`supervise`, `status`): events come from registered sources. The built-ins (`discord`, `github`, `sweeps`, `waits`, and `emit`, the spool `dori emit` writes) record their last event and errors; the `poll`, `webhook` and `file` sources in `<stateDir>/sources.json` (`dori source`) run in the polling task. Every event goes through the journal's dedupe and `eventPolicy`. A source that throws is isolated: it is shown as failing in `dori status` and `/status`, one digest `SOURCE_FAILED <name> <type>: <error>` is journaled when it starts failing (built-ins report their errors as before), and the other sources keep running. Per-source state is in `<stateDir>/sources-status.json`.
- **Schedules** (`supervise`, `status`): the `schedule` sources managed by `dori schedule` run in the polling task (scheduled jobs inside Dori instead of system cron). Each run is an operation row in the store (`schedule:<name>/schedule-run/<slot>`), so a job's last run survives restarts, its next run follows from it, and no slot runs twice; `dori status` lists every job with its next run.
- **Lane reports** (`report`, `watch`, `supervise`): structured lane reports (design 3.3). `dori report <key> <kind> --text T` writes one row (see `dori report`) and the supervisor routes it in its 5 s polling pass: `question` and `blocked` become urgent `LANE_REPORT <key> <kind> <text>`, `milestone` a `LANE_REPORT` classed by `eventPolicy` (`LANE_REPORT * milestone` and `LANE_REPORT * progress` are `lead-digest` unless `eventPolicy` names them), `progress` is posted to the lane's thread through `hooks.threadReply` (no hook, no thread or a failed post: a digest `LANE_REPORT ... progress` instead), and `done` is the lane's done claim, as `dori claim-done`. A row from a lane that is closed or not registered is no longer dropped: it becomes `LANE_REPORT_LATE <key> <kind> <text>` (event id `lane-report-late:<row id>`, route `late`; urgent for `question`, `blocked` and `done`, digest otherwise) and does not count as hearing from the lane. A row whose routing throws is logged as `LANE_REPORT_ERROR <id> <message>`, stays pending and is tried again on the next pass; the other rows are still routed. A remote lane's `[REPORT]` lines are read as a sequence: every line on its screen not acted on before is acted on, top to bottom, each told apart by (lane, line hash, first-seen) in the `remoteReportsSeen` registry field, so two reports printed between two polls both arrive, in order; a lane read by an older dori (newest line only) replays nothing. `launch` gives a new local lane the `dori report` footer (report with `dori report`, never by typing into the lead's pane; done is `dori report <key> done --evidence E`) and records `reportVia: "cli"` on it; remote lanes keep the `[REPORT]` footer. Such a lane's `[REPORT]` lines found in the lead's pane are counted by the `lead-pane` sweep: each distinct line once, as `leadPaneViolations` on the lane and a digest `LANE_PANE_VIOLATION <key> <count> <line>` (the sweep reads the lead's pane only while such a lane is open). Lanes on the older footer keep typing `[REPORT]` lines, which keep working.

## Discord commands

The library modules are listed in [development.md](development.md).

### Discord `/status`

Registered next to `/quota` and handled the same way (owner only, ephemeral, same per-channel rule). It replies with the `dori status` text in a code block, bounded to 2000 characters. It is paged: page 1 (no option) is the report with its first lanes, and its lanes section ends `- +N more on pages 2-T` when more lanes are open; `/status page:N` (integer option, at least 1) starts `Dori lanes - page N of T - <time> KST`, then `Lanes (<count>), continued` and the next lanes in order, as many as fit 1,900 characters, with `Next: page N+1` until the last page. A page past the end says how many pages there are. The supervisor passes it `statusLookup`; without one the command is ignored. The option is part of the guild registration, so a supervisor restart re-registers it.

### Discord button hooks

`dori send discord ... --buttons JSON` posts buttons whose `custom_id` `dori:hook:<name>:<arg>` names a `buttonHooks` entry that runs on click. `<arg>` is 1-70 of `A-Za-z0-9._:-` and travels in the id, so a click works after any restart with no stored state. `dori supervise` handles the click on its gateway without the lead:

- A non-owner (or a foreign application or guild) gets an ephemeral refusal; an unconfigured `<name>` gets the ephemeral reply 알 수 없는 버튼입니다. Nothing runs.
- From the owner: the message is updated at once (content kept, every button disabled, the clicked one relabelled `<label> - 접수됨`), then the hook runs.
- Running the hook spawns `buttonHooks[<name>]` detached, no shell, with `{name}`, `{arg}`, `{channel}` (the message's channel, the thread id in a thread), `{message}` and `{interaction}` replaced in each element. Its stdout and stderr go to the supervisor log as `BUTTON_HOOK <name> ...` lines, and its exit as `BUTTON_HOOK <name> exited <code>`. Then the journal gets `BUTTON_CLICKED_BY_OWNER <name> <arg>` (id `discord:<channel>:button:<interaction>`).
- A failed update of the message leaves the buttons live and runs nothing, so the owner can click again.

## Commands

### `dori doctor`

Read-only health check; it never starts, stops or edits anything and never prints a token. Each line is `OK`, `WARN` or `FAIL` and a non-OK line is followed by `fix: <exact command or step>`. Exit 0 when nothing is FAIL, otherwise 1. Every probe is bounded (5 s per command, 10 s per Discord request).

Checks: `herdr-server` and `dori-supervisor` enabled and active; a legacy `dori-presence` unit or stray `dori presence` process (WARN, double-gateway risk); herdr reachable with one server process; the supervisor unit's WorkingDirectory, `defaultCwd` and `stateDir` exist; config keys (`leadPane`, `laneWorkspace`, `defaultModel`, `discordChannels`, the discord ids) and the lead pane in herdr; `DORI_DISCORD_TOKEN` in `~/.dori/env` works (`GET /users/@me`), the bot is in the guild, every `discordChannels` id is readable; the Message Content flag on `/applications/@me` (WARN with the Developer Portal step); `/quota` and `/status` registered in the guild (WARN: restart the supervisor); the lead's memory (`memoryCheck`): `human.md` found and within `maxKb` (WARN when it is missing or over); the gateway heartbeat is fresh and connected (FAIL if missing or older than 60 s); `gh` installed and authenticated, `jq`, `bun`; free disk against `guard.diskFreeMinGb` (WARN). `dori setup` runs it at the end and prints the report.

### `dori status [--json | --page N]`

`--page N` prints the same page as `/status page:N`. `--json` lists every working lane; each lane carries `report`, its latest `dori report` row (highest seq: `id`, `seq`, `kind`, `text`, `evidence`, `at` and, once routed, `consumedAt` and `route`), read from `lane-reports.json` or the `lane_reports` table opened read-only.

One screen, read-only, no LLM, times in KST (fixed +09:00), written as a short report: one line per item under titled sections. It opens with `Dori status - 10-21 09:53 KST` and a verdict line, `All good. 1 lane working, no waits.` or `Needs attention: <what>. ...` naming the first three problems (a service not running or not enabled at boot, an active legacy `dori-presence`, a gateway that is not live, GitHub poll failures, no trusted `githubIssueAuthors`, a missing or unknown lead, unacked owner messages, unreported lanes, lanes in recovery, failing sources). Then, in order: `Problems` (one line per problem, only when there is one); `Services` (`herdr-server` and `dori-supervisor` as `running`, `stopped`, `failed`, ..., plus `not started at boot` when not enabled; the legacy unit only while it runs); `Lead` (pane, `active` or `idle` against `cacheTtlMin` with the time since its last turn, `stopped` when no agent runs in the pane, last context tokens against `leadContextCapTokens`, and a pending `dori lead-restart`); `Lanes (N)` (one line per working lane: `- <key> (<age>, <short model such as opus-5-5>, <repo> #<PR>): <last progress>`, the repo when the Done signal or worktree names it and `#PR` only for an explicit `/pull/N` or `pr view N` in the Done signal, since a `(#N)` in a lane title may be a task or issue id; a lane in recovery starts with `[recovery gave up]` or `[recovery pending]`); `Waits (N)` (`- <key>: fires <KST> (in <time>)` from the epoch in a `[ $(date +%s) -ge N ]` signal, else `on signal, times out <KST>` from the wait's `deadline` (its timeout, not its fire time), else `until <clipped signal>`, then ` - <note>`); `Schedules`; `Gateway and repos` (Discord gateway, GitHub repos and last poll, issue watching, event sources); `Activity (last 24h)`. Long text is cut at a word and marked `...`, never mid-line, and lists end `+N more` so the text stays under 1900 characters; a text still too long drops whole lines from the end and says `(rest not shown)`. `--json` prints the same data (additive fields: lane `repo`/`pr`, wait `note`) and is unchanged by the layout. The supervisor answers the Discord `/status` command with this text, which the command wraps in a code block.

When the last 24 h journaled any event, `Activity (last 24h)` holds `- Lead woke <n> times, <calls> model calls per wake` and `- Busiest: <kind> <events> events, <wakes> wakes; ...` (the top five kinds as `eventPolicy` names them). A wake is a delivery that starts a lead turn (events appended for an idle warm lead, or a confirmed cold start, `(restart)` when it carried no event); it is triggered by its urgent kinds, else by its overdue digest kinds, and counts once for each. Its calls are the assistant records the lead session wrote from the wake to the next wake, counted when that next wake starts (`?` until then). Wakes live in the store (`lead_wakes`, 30 days; the json store appends `lead-wakes.jsonl`); `--json` gives the full table, with calls per kind, under `events`. Under `Gateway and repos`, `- Event sources: <name>[ (<type>)] <last kind> <age>, ...` lists every source (built-ins first; `no events yet` for a source with none, `FAILING` while it fails); each failing source is a problem line `Source <name> failing since <age>: <error>`, and an unreadable `sources.json` is one too. `Schedules` has one line per scheduled job, `- <name>: next <MM-DD HH:MM> KST (in <time>)[, last run <result>]` (`waiting for a heavy slot` while a due heavy job waits; the last result is shown unless it was `ok` or `emitted`). The same text is `/status` in Discord.

When the config has a `runners` section, a `Runners` section lists one line per runner from the hub's table: `RUNNER <label> <connected|stale|offline> proto=<n> version=<v> gen=<n> hb=<sec> outbox=<unacked>/<oldest sec> cmds=<n> restarts1h=<n> lanes=<n>`, unknown values as `-`. `connected` means a heartbeat younger than 60 s and no disconnect since, `stale` under 180 s, otherwise `offline`.

### `dori runner serve [--label LABEL] [--enroll] [--connect ws://HOST:PORT]`

The runner, shadow only for now (see [runner-protocol.md](runner-protocol.md)). It checks `~/.dori/runner` (dirs 0700, files 0600, no symlinks; otherwise `RUNNER_DIR_UNSAFE` on stderr and exit 1), bumps its boot generation, prints `RUNNER_SERVE label=<l> gen=<n> mode=<m> endpoint=<socket or url>` and connects to the supervisor over `~/.dori/runner/sock/control`, or with `--connect` to the supervisor's `runners.listen` WebSocket, reconnecting with backoff. Every connection runs the signed handshake; a runner that was never enrolled exits 1 with `RUNNER_NOT_ENROLLED`. `--enroll` first reads the `code=` and `fingerprint=` lines of `dori runner enroll` from stdin, enrolls (`RUNNER_ENROLLED`) and then serves; the local runner is enrolled by the supervisor itself. Commands are checked against `~/.dori/runner/runner-config.json` and answered with `RUNNER_CMD_REJECTED <rule>` or, for now, `RUNNER_CMD_UNSUPPORTED <type>`. It heartbeats every 15 s and, when `runners.mode` names its label `shadow`, reports lane observations every 30 s. It changes nothing. The label defaults to `local`. `templates/dori-runner.service` runs it as a user unit; setup doesn't install that unit yet.

### `dori runner enroll --machine LABEL` / `revoke LABEL` / `rotate LABEL` / `reset-gen LABEL`

Runner key management on the supervisor's host. `enroll` prints a one-time code (valid 10 minutes, for that label only) and the supervisor key fingerprint as `code=` and `fingerprint=sha256:` lines on stdout (`RUNNER_ENROLL_CODE` with the expiry on stderr); pass that text to `dori runner serve --enroll` on the runner's stdin, never as an argument. `revoke` deletes the runner's key, closes its connection and refuses its later hellos (`RUNNER_REVOKED`). `rotate` has the connected runner switch to a new key and prints `RUNNER_KEY_ROTATED runner=<label> key=<fingerprint>`, or `RUNNER_ROTATE_FAILED`/`RUNNER_ROTATE_PENDING` with exit 1. `reset-gen` forgets the runner's highest boot generation after its state was restored from a backup (`RUNNER_GEN_RESET`). An unknown label exits 1 with `RUNNER_UNKNOWN`. `revoke` and `rotate` reach the running supervisor within about 5 seconds.

### `dori repos add <owner/repo>` / `dori repos remove <owner/repo>` / `dori repos list`
Manages this machine's extra GitHub repos in `<stateDir>/github-repos.json`, a private JSON array written atomically. Names are trimmed, lowercased, validated as `owner/repo`, and deduplicated; URLs and paths are rejected. Adding an existing repo or removing an absent one is safe. Commands print the resulting JSON list. The supervisor rereads it each polling tick, so changes need no restart; repos inferred from registry lanes are watched separately and are not removed by this command.

`dori setup` asks for an optional comma- or whitespace-separated list after choosing the state directory. A fresh setup defaults to empty; reruns show and preserve the current list. Use `dori repos remove` to remove individual entries.

The supervisor uses conditional `gh api` requests and keeps ETags and last-seen PR snapshots in `<stateDir>/github-events.json` (on the sqlite store: its `gh_*` tables). Keep this file and the existing supervisor queue/log across restarts. Lane PRs come from merged signals or GitHub worktree/head branches. `GH_PR owner/repo#N kind detail url` lines for PRs closed without a merge and other people's comments/reviews are urgent; merged PRs (each lane PR's merge is read back as `MERGE_VERIFIED`, see Merge read-back), lane check failures and conflicts (CI follow-up messages the lane first), opened PRs, green checks and other updates wait for the next urgent delivery. Bots, the authenticated user and the repository owner are filtered from review/comment wakes. `HOST_GITHUB` failure notes are digest-only and limited to one per repo per 15 minutes.

The same poll lists each repo's issues (`issues?state=all`, ETag-cached; pull requests in that list are skipped). The first issue poll of a repo, including a repo that was already watched before this feature, records a baseline and emits nothing. After that, a new open issue or a reopened one by a `githubIssueAuthors` login emits urgent `GH_ISSUE owner/repo#N opened|reopened author=<login> <url>`; any other author emits digest `GH_ISSUE_UNTRUSTED` with the same fields. Lines never carry the title or body, which are untrusted text. Event IDs are `github-issue:<repo>#N:opened` and `...:reopened:<count>`, so a restart or a crash before the snapshot save does not deliver twice. An issue poll failure counts as the repo's poll failure (`HOST_GITHUB`), and the next good poll clears it.

### `dori launch <key> --title T --brief FILE --done "..." [--thread REF] [--mode ulw|mass-ulw] [--model M] [--cwd DIR] [--machine LABEL|ID] [--pane ID | --workspace ID | --toodo-start FILE-OR-JSON] [--share-thread] [--allow-repo-mismatch]`
Opens a lane: appends the footer to the brief, opens a tab, starts the agent, and after 20 seconds checks it: `STARTUP_ERROR` on a known failure in the pane, `STARTUP_OK` when herdr reports the agent working, or idle with no failure on its screen, and `STARTUP_UNCONFIRMED` (with the last lines) otherwise. Exit 3 on anything but `STARTUP_OK`. `--mode` picks the prompt's opening keywords: `ulw` (default, `launchKeywords`) or `mass-ulw` (`massLaunchKeywords`); anything else exits 1. A held launch keeps its mode in the queue (`mode=mass-ulw` in `LAUNCH_READY`).

Launch validates the key, duplicate registration, Done syntax and thread sharing before checking the guard, so an invalid request never enters HOLD. Then it picks the machine (`placement` in the config): `--machine` wins (`source=flag`); a workspace task (`--cwd`, `--pane`, `--workspace`, or a repo on the Done line) follows `placement.workspaces` (`source=workspace`, with `rule=<key>` when one matched); anything else goes to `placement.defaultMachine` (`source=default`). It prints `PLACEMENT machine=<m> source=<source>[ rule=<key>]` and checks that machine's guard (memory, disk, pane count; a remote machine is sampled over ssh, its panes counted with `herdr --machine <label> pane list`). Only a default placement can move: on HOLD it tries `placement.fallback` in order and takes the first machine with room, printing `PLACEMENT_FALLBACK <from> -> <to> (<from reasons>)`. A pinned or workspace launch stays put. HOLD is per machine. On a HOLD, launch prints `HOLD <reasons>` for local or `HOLD machine=<label> <reasons>` for a remote machine and `QUEUED <key> (<n> waiting; dori hold list)`, atomically adds the request and raises that machine's blocked flag in `launch-hold.json` (the queue entry keeps `machine` for a remote target), and exits 4; the queue entry leaves when that lane launches or is dropped. If `launch-hold.json` can't be parsed or has the wrong shape, it's moved aside to `launch-hold.json.corrupt-<ms>` and `LAUNCH_HOLD_CORRUPT moved <path> to <aside>: <error>; continuing blocked with an empty queue` goes to stderr. Launches stay held until the guard clears, and any queued work in the old file has to be launched again by hand. A single bad queue entry is dropped instead (`LAUNCH_HOLD_INVALID_ENTRY`), and the valid ones stay. With `guard.panesMax` at 0 or below every local launch prints `LAUNCH_WARN`.
Before writing the footer or creating a tab or agent, launch rechecks admission and reserves its key, thread and checkout under one lock shared with adopt. A pending launch is recorded as paused with `launchReservation`, preventing automatic recovery from spawning it. Success replaces the reservation with the launched lane; failure before agent admission releases only its own reservation. A process crash or registration failure after agent admission leaves the paused reservation visible for inspection instead of silently starting another agent; the pane and tab are recorded before agent admission.
`--thread` is stored as `discord:<channel>/<thread>`: a value naming only the thread (`discord:<thread>` or a bare id) gets its parent channel from Discord (`GET /channels/<id>`); without a token or an answer it is kept as `discord:<thread>` and `THREAD_PARENT_UNKNOWN <id>: <why>` goes to stderr. A lane record written by an older launch with a bare thread id reads as `discord:<id>`, and its next registry write stores it so.

Placement checks (launch and adopt, skipped for remote lanes and directories outside git): another open lane on the same thread (compared by thread id) is refused unless `--share-thread` (recorded as `threadSharedWith`); a cwd in the same checkout as another open local lane is refused; a cwd whose git remotes name none of the `Done =` repos is refused unless `--allow-repo-mismatch`. A local lane starts with `DORI_LANE_KEY=<key>` in its environment.
With `--pane ID` (or `--workspace ID`, resolved to its only pane without an agent) the same command runs in that existing pane instead of a new tab: use it for an existing worktree session such as one another tool created. `--cwd` defaults to the pane's cwd. It refuses, writing no footer and no registry entry, when the pane is missing, runs an agent or any other foreground process, is already registered to a lane, or `--pane` and `--workspace` disagree.

With `--toodo-start FILE-OR-JSON` (the saved response of the Toodo `start_task` call the lead made, raw or as the MCP result with `structuredContent` or a JSON text content) the lane runs in that task's worktree (`worktreePath` becomes the cwd) and in the first listed pane without an agent, so no second worktree or tab is made. It cannot be combined with `--cwd`, `--pane` or `--workspace`. When that pane is gone or busy (pane ids do not survive a herdr restart), it takes the one shell pane of the task's `herdrWorkspaceId` and prints `LAUNCH_PANE_REFOUND <key> pane=<id>: <why>`; when there is no usable pane (`panes` empty or `paneError`, as with runner plain, tmux or none, or herdr down) it opens a new tab in the worktree and prints `LAUNCH_FALLBACK <key> new tab: <why>`. A task on a remote workspace needs `--machine` naming its herdr machine, so the pane lookups and the tab go to that machine; a `worktreePath` that does not exist on this host without `--machine` is refused.
The failure scan runs for every status but working (an agent that printed "No API key" or a usage-limit error and stopped at its prompt reads idle), and it skips `Tip:` lines, recalled-memory/Kibitzer blocks and echoes of the launch prompt; bare words such as `quota` count only after `Error:`.
With `--machine <label-or-id>` the lane runs on a saved herdr machine. It works with `--pane`/`--workspace` on that machine, or as a plain launch, because `herdr tab create` accepts a machine. A plain remote launch does not reuse the local `laneWorkspace` ID. The brief is read locally and copied with its footer to the target machine through the pane's shell, never by the lead's own path: launch reads the pane's shell from `herdr pane process-info` (a drive-letter cwd such as `D:\...` counts as PowerShell when no shell name is readable). In PowerShell (`pwsh`, `powershell`; 5.1 and 7) it sends one ASCII line that writes the brief as base64 bytes to `<temp dir>\dori-brief-<key>.md` and then starts the agent, so no brief character is ever parsed by the shell; any non-ASCII agent argument also travels as base64. A POSIX shell gets `printf ... > /tmp/dori-brief-<key>.md && <agent>`. A `cmd.exe` pane is refused before anything runs. The agent's prompt names that remote path. `--cwd` is the directory on the machine: it goes to the remote `herdr tab create` and is stored as `remoteCwd` (a plain launch without it stores the new pane's own directory), while the lead's `defaultCwd` is never sent there. The local MCP optimization is skipped for remote lanes.
A remote lane's footer asks it to print its `[REPORT]` lines in its own pane (the freshness sweep reads them from there) instead of messaging the lead pane, and to print `[REPORT] <key> | done | ...` instead of running `dori claim-done`, which does not exist on that machine. The lead checks the `Done =` signals and closes it with `dori close`. Local footers are unchanged.

### `dori adopt <key> --pane ID --title T --brief FILE --done "..." [--thread REF] [--cwd DIR] [--machine LABEL|ID] [--share-thread] [--allow-repo-mismatch]`
Registers a lane that is already running. Add `--machine` when the pane lives on a saved machine; `--cwd` is then its remote directory, stored as `remoteCwd`.

The lane's machine is stored in its registry entry, and every command that reads or messages the pane (`sync`, `claim-done`, `object-done`, `close`, `pause`, the watcher and supervisor) uses it. Entries without a machine stay local. For remote lanes, worktree git checks and cleanup are skipped with an explicit detail instead of being run against a local path that happens to look the same. Their `command` Done signals run on this host in `defaultCwd`, never in the remote path (older entries that stored the remote path as `cwd` included), so `dori close` works for them.

### `dori sync [--write]`
Prints `key | thread | pane | session | status` for every open lane and every unregistered agent pane, followed by drift. Read-only unless `--write`, which stores session ids.

### `dori claim-done [<key>] --evidence TEXT` / `dori object-done <key> --reason TEXT ...`
The two halves of the done flow. Both message the lane's pane and check that Enter registered; nothing is typed into a pane that is missing, unreadable or has no live agent (a bare shell would run it), or whose input line holds other text. The objection's reasons are never typed: the lane hears a fixed `[LEAD] not done` sentence and reads them with `dori lane status <key>`.

### `dori lane status [<key>]`
Prints the lane's key, status, last objection (`at`, `reasons`) and done claim as JSON. Inside a lane it reads only its own key (the default).

### `dori close <key> [--note TEXT] [--force]` / `dori close <key> --cancelled --reason TEXT [--force]`
Closes a lane now. Refuses (exit 2) unless every `Done =` signal reads back live. It then checks the worktrees like the watcher does: uncommitted, untracked (gitignored files don't count) or unpushed work prints `REFUSED <key>: unpushed work in <wt> ...` and touches nothing. Next it removes the worktrees; a failed removal prints `REFUSED <key>: worktree <wt> not removed: ...` and leaves the pane, thread and lane open. Only then does it close the tab and record the lane closed; the thread is left open (see Thread left open). `--force` closes past unpushed work and keeps a worktree it can't remove (the watcher cleans it later).

A lane whose cwd no longer exists (its worktree was removed) is checked in `defaultCwd` instead: the close prints `SIGNAL_CWD <key>: lane cwd <dir> no longer exists; Done signals and git ran in defaultCwd <dir>` and its `command` signals and git calls run there, as for a remote lane.

`--cancelled --reason TEXT` (lead-only; a lane gets `LANE_PERMISSION_DENIED`) closes a lane whose work was cancelled or whose `Done =` can never hold. It does not run the Done signals (`SIGNAL SKIPPED <key>: cancelled by the lead: <reason>`); the worktree checks, cleanup and `--force` work as above. The lane is recorded closed with the history note `cancelled: <reason>` (unless `--note` is given) and `cancelled: { reason }` in its receipt, and prints `CLOSED <key> cancelled`. Like every manual close it emits no `LANE_CLOSED`, so no outcome report is owed; `dori reported <key>` still posts one if the owner should hear it. Without `--cancelled` the close stays strict.

Each close holds a per-lane lock (`lanes/<key>.close.lock.sqlite`), records its intent first (a `<key>/close/<key>` row with the note and `--force`) and runs each effect as an operation keyed by what it acts on (`<key>/worktree-remove/<path>`, `<key>/tab-close/<tab>` or `<key>/pane-close/<pane>`). A verified operation never runs again; a read-back that already shows the effect in place verifies it without acting. The automatic close records its intent before the lane reads `verified-done`. After a crash anywhere in the sequence, the next watcher pass (supervisor or `dori watch`) reconciles every row left attempted by reading the world back: the worktree path is gone, the pane or tab is no longer in `herdr pane list`. Done verifies it and not done allows the retry. Then the close runs again with its recorded note: `LANE_CLOSED` when it finishes, urgent `OPERATION_AMBIGUOUS <id> <detail>` when it stops at an operation nobody can tell happened (the effects after it do not run), urgent `OPERATION_FAILED <id> ...` when the resumed close is refused. Each is emitted once.

Inside a lane (`DORI_LANE_KEY`, or the pane registered to a lane), `claim-done`, `object-done`, `close`, `pause` and `resume` accept only the lane's own key; another key exits 1 with `LANE_PERMISSION_DENIED`. `ack`, `handled`, `reported`, `send`, `launch`, `adopt`, `hold`, `ops` and `lead-restart` are lead-only: a lane gets `LANE_PERMISSION_DENIED lane <key> may not run <cmd>; it is lead-only` and exit 1. Read-only commands, `wait`, `status`, `guard`, `can-launch`, `heavy` and `report ack` still work, and `report <key> <kind>` accepts only the lane's own key. The lead has no limit.

### `dori ops [list] [--lane KEY] [--all] [--json]` / `dori ops resolve <id> --as verified|retry`
Lists operation rows, one `OP <id> <state> attempts=<n> <updated> <detail>` line each (or `OPS none`): planned, attempted, failed and ambiguous ones; `--all` adds verified ones, `--json` prints the rows. States: `planned` (intent recorded) -> `attempted` (durable before the effect) -> `verified` | `failed` (read back not done; a later close may retry) | `ambiguous` (interrupted, or run and the read-back cannot tell). After an effect runs, the read-back alone decides: done is `verified`, not done is `failed`, and unknown is `ambiguous` whatever the effect reported (it threw, failed or said it succeeded), so an effect that may have happened is never retried or taken as done on its own word. `resolve` is the lead's answer for an ambiguous or failed row after checking the world by hand: `--as verified` (the effect is in place; it will not run again) or `--as retry` (it did not happen; the next close runs it). Then run `dori close <key>` to finish. There is no generic undo: a wrong irreversible effect is repaired by hand (re-create the worktree from the pushed branch, reopen the thread).

### `dori report <key> <progress|question|blocked|milestone|done> --text T [--evidence E]`
A lane's structured report. Inside a lane only its own key is accepted (`LANE_PERMISSION_DENIED` otherwise); the lead may report for any lane. The text and evidence keep their newlines (surrounding whitespace is trimmed; secrets are still redacted). Each row carries the lane's current generation. It prints `LANE_REPORTED <id> <kind>` once the row is durable; routing is the supervisor's (see Lane reports under Always-on behavior). A routed row counts as hearing from the lane (`lastReplyAt`), like a thread reply. A report longer than 200 characters or 3 lines reaches the lead as a summary plus `(full report: <stateDir>/reports/<id>.txt)`. A row stuck for 3 passes raises urgent `LANE_REPORT <key> blocked REPORT_STUCK <id> ...`. A row from a replaced session (older than the lane's `lastRecoveryAt`) arrives as `LANE_REPORT_LATE ... (from a replaced session)`. On the sqlite store `lane_reports` gains an `event_id` column (added automatically); JSON rows gain `eventId`.

### `dori resolved <eventId> [<eventId> ...] [--note TEXT]`
The lead's receipt that it decided a decision event (see `resolveKinds`). Each id is written as an immutable receipt in `<stateDir>/resolved/` (tmp, fsync, rename), which the supervisor consumes on its next pass. It prints `RESOLVED_RECORDED <id>` for an id among the open decisions the supervisor last published (`<stateDir>/unresolved.json`), else `RESOLVED_UNMATCHED <id>: no open decision has this id; recorded anyway`: a receipt that arrives before its event still closes it, so that event opens nothing. A resolved decision is kept 7 days for that dedupe. Open ones are listed by `dori inbox take` as `unresolved:<id><TAB>UNRESOLVED <id> since <ISO>: ...` lines and join every cold-restart handoff; no reminder is sent while a lead restart runs.

### `dori event trace <eventId> [--json]`
Read-only, no lock: one event's path through the supervisor, from whichever store holds the journal. Text output is `EVENT <id> <line>`, `META k=v ...` when the event carries lane metadata, one `<ISO time|-><TAB><step><TAB><detail>` line per step, then `OPEN <steps still owed>`. Steps: `enqueued`, `delivered` (in `lead-events.log`; the json store has no delivery time, shown as `-`), `taken` (from a consumed `dori inbox take` receipt, with its session), then `acked` / `handled` / `deleted` for an owner message or `reported` for an event in a finished lane's report obligation; a body moved to a tombstone shows `pruned`. `--json` prints the trace object. An unknown id prints `EVENT_NOT_FOUND <id>: ...` and exits 1; a store that cannot be read prints `EVENT_TRACE_UNAVAILABLE` and exits 2. Take times live in sqlite `deliveries.taken_at` / `taken_session` (schema 6) or, on the json store, `<stateDir>/lead-takes.jsonl`; the first take of an id wins.

Rows live in `<stateDir>/lane-reports.json` (`{"reports": [...]}`, rewritten under a short state lock), or on the sqlite store in the `lane_reports` table of `supervisor.sqlite`, created on first use (no schema migration):

| Field (column) | Meaning |
|---|---|
| `id` | `<lane>:<generation>:<seq>`; the routed event's journal id is `lane-report:<id>` |
| `lane` | the lane key |
| `generation` | the lane's ownership generation (design 4.2); 0 until ownership fencing lands |
| `seq` | 1, 2, 3, ... per lane, in write order (unique per lane) |
| `kind` | `progress`, `question`, `blocked`, `milestone` or `done` |
| `text`, `evidence` | one line each; `evidence` is optional (for `done` it is the claim's evidence, else `text` is) |
| `at` | write time, ms since the epoch |
| `consumedAt` (`consumed_at`) | when the supervisor routed it; unset while pending |
| `route` | `journal` (a LANE_REPORT event), `thread` (posted by `hooks.threadReply`), `claim` (done claim) or `dropped` (its lane was closed or unregistered) |

Rows are routed oldest first (`at`, then lane and `seq`) and marked consumed after the effect: a crash in between repeats it (the journal dedupes the event by id; a thread post may show twice).

### `dori report ack <id>`
Inside a lane only: confirms a supervisor message to this lane (CI follow-up), named by the ID at the end of the message. Prints `LANE_MESSAGE_ACKED <key> <id>`; an unknown ID or a message addressed to another lane exits 1. Only this ack counts as confirmation: pane activity never does, and an unconfirmed message reaches the lead after `ciConfirmMin`. A lane on another machine cannot run it; its messages reach the lead after the deadline.

### `dori pause <key> [--note TEXT]` / `dori resume <key> [--note TEXT]`
`pause` is for when the owner said wait. It works on a `working` or `not-done` lane. It sends `/goal pause` to the lane's pane, then reads the screen back until the goal command's own line appears on a line of its own: `Goal paused`, or `cannot update goal: no goal exists`, since a lane with no goal has nothing to continue. Only then does it mark the lane `paused` (recorded in its history) and, if a turn is running, send Escape and read the pane back until it is no longer `working`. The goal is paused first, so stopping the turn cannot hand off to a goal continuation. If the line does not appear, or the send fails, the lane is left as it was and the command prints `PAUSE_UNVERIFIED` and exits 3. If the goal is paused but the turn is still running after Escape, the lane stays `paused` (the sweep below keeps interrupting it) and the command also prints `PAUSE_UNVERIFIED` and exits 3; a repeat `pause` on a paused lane that reads `working` sends Escape again.

A paused lane is skipped by `freshness`: no nudge, no post. Only `dori resume` ends a pause, on the owner's word. Activity never does, because a paused lane can still be woken by a background result, a monitor event it armed before the pause, or a queued message. Every `freshness` tick that finds a paused lane `working` interrupts it again: Escape, then a read-back. If it was `working` on two ticks in a row, or Escape did not stop it, `freshness` prints `WORKING-WHILE-PAUSED` with the result (`re-interrupted, its turn stopped`, or `PAUSE_UNVERIFIED: Escape did not stop its turn`) once per working stretch (again after it goes idle and is woken, or after a new pause), so the lead can ask the owner, and the lane stays paused.

`resume` sends `/goal resume` and reads back `Goal active` the same way, then restores the status the lane had before the pause (`pausedFrom`) and restarts its quiet time, so a long pause does not turn into an instant nudge. Unconfirmed: `RESUME_UNVERIFIED`, exit 3.

Both print `PAUSED` / `RESUMED` and exit 0 on success. A lane in any other state is refused (`NOT_PAUSED` / `NOT_RESUMED`, exit 2), and a second `pause` is a no-op. `claim-done` and `object-done` on a paused lane move it out of `paused` in the registry while its goal stays paused.

### `dori supervise`
Runs supervised mode. One Discord gateway connection owns online presence, slash-command interactions and inbound messages from `discordChannels`, every thread under those channels, and open registry threads. The same process runs `watch`, `guard`, `dead-panes`, and `freshness`, and appends what the lead needs to act on to `<stateDir>/lead-events.log`. It starts the lead on `leadModel` (else `defaultModel`) with a startup prompt that lists pending events and gives the exact monitor command, `tail -c +N -F <path>`, where `N` is the byte offset of the handoff. The lead runs that command as given rather than `tail -n 0 -F`, so no event falls into the gap before its monitor registers. Don't run standalone presence, sweeps or an inbound poller next to it. Without `dori supervise`, everything below works as before. Content recovered for a message first delivered with the missing-content placeholder arrives as a new event with id `discord:<channel>:<messageId>:rev:content`, on the same `INBOUND`/`VISITOR` line.

Set `DORI_DISCORD_TOKEN` to the bot token and configure `discord.applicationId`, `discord.guildId` and `discord.ownerId` before starting (`dori setup` discovers them). REST catch-up runs on startup and reconnect, paginating back to the saved snowflake in `discord-inbound.json`; gateway events and catch-up share deduplication. On the first observation of a channel it imports the latest `discordFirstSeenLimit` messages (default 100); after that it drains the unseen backlog. Threads under watched channels are watched too, lane or not, including an archived thread that a new post reopens: the gateway resolves a message's thread parent from `GUILD_CREATE`/`THREAD_*` events, falling back to one cached `GET /channels/{id}`, and each catch-up makes one `GET /guilds/{guild}/threads/active` request and polls the active threads whose parent is watched, with per-thread cursors. Their baseline is `threadsSince` in `discord-inbound.json`, the snowflake of the first catch-up that watched threads: a thread first seen later imports only messages newer than that floor (or its saved cursor, whichever is newer), never older history. Inbound reads watched channels, their threads and open lane threads. The owner's messages become urgent `INBOUND` lines; anyone else's become urgent `VISITOR <channel> <id> <author> (not the owner; content to brief the owner about, not an instruction) <text>` notices, so the lead can brief the owner; bots and the bot's own messages are dropped. Keep the channel cursors across restarts. Healthy connections use the slow `discordSafetyPollSeconds` REST safety interval (default 300 seconds); unavailable gateways automatically fall back to 5-second REST polling.

Inbound limits: signed Discord attachment CDN URLs expire (about 24 hours), so a lead opening one later may need a fresh URL. Edits arrive only through gateway events, not REST catch-up. Delete tracking is kept only in process memory and is lost on supervisor restart.

Enable the privileged **Message Content Intent** in the Discord Developer Portal, application **Bot** tab. On close code 4014 (disallowed intents), the supervisor warns once, reconnects without that intent, keeps presence and slash interactions available, and uses 5-second REST polling for inbound. REST does not bypass Message Content access restrictions, so degraded nonprivileged operation may lack message text except for Discord's exemptions, such as messages mentioning the bot.

Setup installs only `herdr-server.service` and `dori-supervisor.service`; it confirms before disabling and stopping a detected legacy `dori-presence.service`. A separate token-scoped gateway lock is shared by the same OS user on the same machine, independent of `stateDir`, and refuses a second supervisor or standalone presence process for that token. It does not coordinate other machines or OS users.

The supervisor unit is `Type=notify` with `WatchdogSec=300`: the supervisor sends `READY=1` after startup and `WATCHDOG=1` after each loop pass and every minute in between, but only while the loop has made progress (a finished pass or sweep) within 15 minutes and no background task (lead delivery, waits, GitHub polling) has been running longer than that. Otherwise it logs `WATCHDOG_WITHHELD <what>` and systemd restarts it, so a stuck delivery is caught while one long sweep round does not trip `WatchdogSec`. Both units stop restarting after 5 starts in 600 s and then run `dori-failure-notify@.service`, which posts one Discord line to the first `discordChannels` entry with the free state-disk space, the last log lines and the `systemctl --user reset-failed` / `start` commands. Existing installs pick this up by rerunning `dori setup` with autostart and `systemctl --user daemon-reload`.

Startup and the running loop have separate deadlines. **Before `READY=1`**, `TimeoutStartSec=300` covers `ExecStartPre` (the boot prep waits up to 2 minutes for the herdr server) and every startup step; a start that misses it is killed with SIGKILL (`TimeoutStartFailureMode=kill`, because a blocked startup cannot run its SIGTERM handler) and restarted 15 s later, about 315 s after it began. **After `READY=1`**, `WatchdogSec=300` applies, and the supervisor withholds `WATCHDOG=1` once the loop or a background task has made no progress for 15 minutes, so a hung loop is restarted 15-20 minutes after its last progress. To name the step behind a hang, the supervisor times each startup step (`lock`, `credential`, `gateway-lock`, `supervisor` (journal and log load), `waits`, `github`, `inbound`, `ready`) and each step of the first loop pass (`loop:inbound`, `loop:heartbeat`, `loop:notice-*`, `loop:sweep:<name>`, `loop:watchdog`). It logs `STARTUP_TIMINGS ready <total>ms <step>=<ms>ms ...` after `READY=1` and `STARTUP_TIMINGS first-pass ...` after the first pass (`startup-incomplete` or `first-pass-incomplete` when it fails or stops early). A step still running after 60 s logs `STARTUP_SLOW <step> still running after 60s (budget 60s)` from a watcher thread, so the line reaches the journal even while synchronous code blocks the main thread. After a hang, `journalctl --user -u dori-supervisor.service | grep STARTUP_` shows the step.

The cold-start prompt points the lead at the full `SKILL.md`. Lead launches reuse `agentCommand` with `leadModel` (else `defaultModel`) and `leadThinking` when set, adding `--session-id` and `--session-dir` to its executable so recovery can identify the exact generation.

An idle lead is warm while its resolved session file's mtime is younger than `cacheTtlMin`; a working lead is always warm. When stale, the next delivery restarts it, even while durable waits are pending or registry lanes have status `working`: their later events (lane reports, `WAIT_DONE`) land in the event log past the take cursor, and the fresh lead's `dori inbox take` keeps reminding it of open decisions (`UNRESOLVED`) and finished lanes not yet reported (`UNREPORTED`). A last recorded `message.usage.totalTokens` at or above `leadContextCapTokens` restarts the idle lead on the next delivery even while its cache is warm, as `context-cap`; missing or unreadable usage is treated as under-cap. A lead still waiting on its own children delivers warm instead of either restart, up to `leadChildWaitMaxMin`. Every restart logs `LEAD_RESTART_TRIGGER <request|hard-cap|context-cap|stale|no-agent|stuck|push-escalate> <why>` before it stops the lead. Blocked or unclassified agents are left alone. A cold idle lead (or an available shell with no live agent) is replaced in the same pane. Only the old agent tree and processes carrying its exact session ID are stopped. Missing identity is an error, not permission for broad cleanup.

Omo's `promptCache.keepAlive` is an optional extra with roughly break-even cost; this setup does not enable it.

The default event policy (`src/event-policy.ts`, changed through `eventPolicy` with no code change) marks owner inbound and visitor notices, `LANE_NOT_DONE`, remote lane blockers and questions (`LANE_REPORT`), a lane waiting on its agent's on-screen question (`LANE_ASKING`), dead and unrecognised panes, `NO-REPORT` (remote lanes only: a local lane reports with `dori report` or into the lead's pane, so its pane having no `[REPORT]` line is no event), `NO-PROGRESS`, `IDLE-ESCALATE`, `MERGE_UNVERIFIED`, `LANE_DONE_CLAIMED`, `LANE_CLOSED` (except the digest kind `LANE_CLOSED * closed seen-claim`), `LANE_AUTO_CLOSED`, `CI_MERGED`, guard alerts and clears (machine guard `HOST_GUARD OFFLINE` and `HOST_GUARD OUTDATED` too), `LAUNCH_READY`, working-while-paused, wait completion/timeout, `SUPERVISOR_STUCK`, `LEAD_UNRESPONSIVE`, `UNHANDLED`, `INBOUND_EDIT`, `INBOUND_DELETE`, `LANE_RECOVERY_EXHAUSTED`, `LANE_RECOVERY_BLOCKED`, `WAIT_FAILED`, `WAITS_CORRUPT`, `OPERATION_AMBIGUOUS` and `OPERATION_FAILED` as urgent. An urgent event starts a delivery. Every other event remains in the durable inbox as digest and joins the next urgent batch, or is delivered on its own once the oldest one has waited `digestMaxDelayMin`.

A lane asks the lead with `dori report <key> question`. One that asks only through its agent's on-screen question UI (omo's ask-user: the blocking `Ask user` dialog, or the `? Question pending (N unanswered)` widget above the editor) wakes nobody, so the `ask-user` sweep reads the bottom of every open lane's pane (paused lanes excepted) and raises one urgent `LANE_ASKING <key> waits on an on-screen question, not dori report: [<header>] <question> | options: a / b` per question. The same prompt still showing is not raised again; once it is gone (answered, cancelled, timed out) the lane's next question is. `LANE_ASKING` is a decision kind: close it with `dori resolved <eventId>` after answering in the lane's pane or telling the lane to re-ask with `dori report`.

The sweeps (`watch`, `guard`, `dead-panes`, `recover`, `freshness`, `ask-user`, `memory`, `lead-pane`, then `machine-guard` last) run every 30 seconds, each on its own: their lines are enqueued as they appear, and a sweep that throws (for example a failed `herdr pane list`) becomes one digest `SWEEP_WARN <sweep> <reason>` (`LANE_WATCH_WARN` for the watcher) and never stops the other sweeps or the supervisor. The same warning is queued at most once an hour, and warnings (any `*_WARN` line, including `DEAD_PANES_WARN` for an unreachable remote machine, whose quiet lanes still raise urgent `NO-REPORT`/`NO-PROGRESS`) never trigger the `digestMaxDelayMin` delivery on their own; stderr logs every occurrence. The watcher writes a claim's announced flag only after `LANE_DONE_CLAIMED` is enqueued. Large startup batches use a private `@file` prompt to avoid terminal input limits.

`supervisor.json` is the durable inbox and restart transaction. `lead-events.log` contains one JSON event per line (`id`, `line`); its stable IDs are the delivery receipts. Delivery means reaching this durable transport (the startup prompt carries no event; the new lead reads them with `dori inbox take`), not that the LLM has completed the requested work. Keep both files and `discord-inbound.json` across supervisor restarts. One OS-backed lock prevents simultaneous writers and is released on process exit, including a crash. An uncertain launch retains its transaction and verifies the same session on restart; it never blindly submits the prompt again. `STARTUP_UNCONFIRMED` requires inspecting that exact session before intervening; after 5 unconfirmed checks of one session that never wrote startup evidence (below) the supervisor saves the lead pane's last 80 lines to `lead-pane-<pane>-<ms>.txt` in the state dir (`LEAD_PANE_SCREEN_SAVED <pane> <path>`), kills only that session's process tree, replaces the pane when only a plain shell is left in it (`LEAD_PANE_RECREATED`, otherwise `LEAD_PANE_KEPT`), and moves the same events to a fresh session id. A pane that vanished while a launch was submitted gets a fresh session id too. A launch is typed only into a plain shell: any other foreground process (an agent started by hand, for example) fails it with `LEAD_PANE_BUSY` and the retry backoff. A launch also needs startup evidence for its exact session within 20 seconds (`session-holders/<session>/<pid>.json` or the session jsonl); without it the supervisor kills only that session's process tree and relaunches once with a fresh session id, the same events and the same tail offset (`LEAD_STARTUP_HUNG_RETRY`). A second miss logs `LEAD_STARTUP_HUNG <session>`, retains the events and leaves the next relaunch to the normal retry backoff. SIGINT/SIGTERM stop polling and release the supervisor lock without terminating the lead.

**SQLite store.** `dori store import` moves a state dir to the store: stop the supervisor first (it refuses with `STORE_SUPERVISOR_RUNNING` while the supervisor lock is held). It records the source cursors (size and sha256 of `supervisor.json`, of `lead-events.log` up to its last complete line, and of `github-events.json`), imports every journal field and every delivery from `lead-events.log`, reads the result back and refuses with `STORE_IMPORT_MISMATCH` unless it equals the source field by field (`STORE_IMPORT_UNKNOWN_FIELD` for a field it has no table for). Only then does `supervisor.sqlite` appear, and `supervisor.json` becomes the read-only `supervisor.json.pre-sqlite`; `github-events.json` moves into the same database (tables `gh_repos`, `gh_prs`, `gh_issues`, `gh_cache`) and stays as the read-only `github-events.json.pre-sqlite`. Lane reports and lane messages move too: every row of `lane-reports.json` and `lane-messages.json`, pending or consumed, with all its fields, goes into `lane_reports` / `lane_messages`, is read back (`STORE_IMPORT_MISMATCH` otherwise), and each file becomes a read-only `<file>.pre-sqlite`; a lane file whose `.pre-sqlite` already exists refuses the import (`STORE_EXISTS`). The import holds the lane-report and lane-message locks, so a `dori report` waits for it. Ids and per-lane seqs are kept, so a lane's next report continues its own seq. A state dir imported before that keeps its `github-events.json` until the first sqlite supervisor start, which imports it the same way under its lock. A refusal leaves the state dir untouched. Then set `"store": "sqlite"` and start the supervisor. `lead-events.log` stays the lead's transport; the store also records each delivery and the log offset it has read, so a restart reads only the log tail and delivers nothing twice. An `enqueue` that returns has saved its event: a failed save restores the journal as it was (owner tracking and lane outcomes included), forgets the id and rethrows, so a retry of the same id is not a duplicate. A source keeps its event for that retry: the `emit` spool file stays, a webhook answers 503. Warnings are saved in the same write as their event. Owner messages (`INBOUND`, edits and deletes) are synced to disk before `enqueue` returns; other writes survive a process crash at once and power loss by the end of the loop pass. `dori status` reads whichever store holds the journal.

**Rollback (`dori store export`).** With the supervisor stopped (`STORE_SUPERVISOR_RUNNING` otherwise), it writes `supervisor.json` and `github-events.json` back from the store and makes `lead-events.log` hold every delivery the store recorded. The sqlite supervisor keeps appending `lead-events.log` as before (it is the lead's transport and the compatibility log), so the log normally stays byte for byte as it was and the lead's tail offset stays valid; a recorded delivery it lacks is appended, and events the store pruned to tombstones are still lines of the log, which a json supervisor recovers at its start. Each file is read back and must equal the store (`STORE_EXPORT_MISMATCH` otherwise, nothing moved into place); Lane reports and lane messages are written back to `lane-reports.json` and `lane-messages.json` when the store has any (read back the same way); an existing lane file holding a row the store lacks or holds differently refuses the export first (`STORE_EXPORT_CONFLICT`), while one whose rows all match is completed. Take times (`lead-takes.jsonl` / `deliveries.taken_*`) are not carried either way. `supervisor.json` is written last, and the database becomes the read-only `supervisor.sqlite.exported` (with its `-wal`/`-shm` files, if any). The report lists what it wrote (size and sha256 of each file) and the store's source cursors (log offset, last GitHub poll, the import record). It refuses a state dir that already has `supervisor.json` or a `supervisor.sqlite.exported` (`STORE_EXPORT_EXISTS`). Then set `"store": "json"`, deploy the previous SHA if rolling back, and start the supervisor.

**Retention (sqlite store).** Unresolved work is never pruned: undelivered events, the events of tracked owner messages (open, acked, quarantined or handled within the last day), a pending restart's events, and open PRs. Once an hour the supervisor moves delivered event bodies older than 7 days to dedupe tombstones (id and time), so a replayed source id is still a duplicate; event and owner tombstones expire after 90 days. GitHub status history keeps 30 days: a closed or merged PR quiet that long keeps its baseline row without its activity ids, and a cached response no poll used for 30 days is dropped. Cached GitHub responses keep only the fields the poll reads. The json journal keeps everything, as before.

A transient lead state (pane missing, old lead not exited, startup or launch admission unconfirmed, session unresolved, non-agent foreground process) does not end the supervisor: it logs one `SUPERVISOR_RETRY` line, keeps events and the restart journal as they are, retries with backoff of 5s doubling to 60s, and recreates a missing lead pane as a `dori-lead` tab in the `Dori` workspace at `defaultCwd` (herdr removes a workspace with its last pane, so a missing `Dori` workspace is created again and its first pane becomes the lead), writing the new `leadPane` back to the loaded config; a herdr refusal is logged as `LEAD_PANE_CREATE_FAILED <reason>` and retried with the backoff. After 10 minutes of the same failure it queues one urgent `SUPERVISOR_STUCK <reason>` and posts it once to the first `discordChannels` entry, scrubbed of home paths and pane ids like every automatic post (the lead's copy keeps them); config errors and a held lock still exit.

The supervisor never speaks for the lead: its only owner-facing output is emoji reactions and lead-status notices (`ownerDelayNotice`, `ackMissingNotice`, `unhandledNotice`, lead-stuck and restart-capped announcements, the `SUPERVISOR_STUCK` notice and the `TASK_STALLED` delivery warning). Finished lanes are reported by the lead alone (`dori reported`); a config still carrying `laneFinishNotice` loads, and the key is ignored with one warning. Owner announcements go through a durable outbox in `supervisor.json`, retried every minute until posted. Every text post the supervisor makes on its own (these notices in Discord, the announcements, `SUPERVISOR_STUCK` and the `TASK_STALLED` warning) starts with `[System] `; reactions and `dori send` posts carry no prefix. A cold start always lists the held launches (`LAUNCH_QUEUE ...`), even after `LAUNCH_READY` lowered the hold flag. Owner edits and deletes revise the tracked message: reminders and cold handoffs carry the latest text, an edit of a handled message is tracked again, and a deleted one counts as handled and is never handed over. Messages handled more than a day ago leave the tracking list for a tombstone. `leadStuckRestartMin` is checked when `dori supervise` starts, before it takes the lock: a bad value stops it with `leadStuckRestartMin must be positive`. A lead that stays busy with unread owner messages for `leadStuckRestartMin` is cold-restarted with them (`LEAD_STUCK_RESTART` in the log) and the owner is told.

An owner message that has not reached a running lead within a minute (delivery failing, or a cold start that has not confirmed) gets `ownerDelayNotice` posted once in its own channel or thread; the message itself stays queued.

**Read receipts.** Every owner `INBOUND` the supervisor appends to the lead's log waits in `supervisor.json` (`awaitingAck`) for the lead's `dori ack`. A message still unacked `ackTimeoutSec` after the handover keeps the lead pushed (no separate event is enqueued); after a second window the owner gets `ackMissingNotice` once in that channel or thread. Nothing escalates while a lead restart runs, and when a cold start confirms (`LEAD_RESTARTED`) every waiting message gets a fresh window, so a slow boot never counts against the new lead. A notice already posted is never repeated, however many restarts follow. `dori status` shows messages reminded and still unacked as a problem (`unacked N`). Entries and stray ack files are dropped after a day.

**Tracking comes from rows, not history.** At startup the supervisor reads owner tracking from its stored rows (`awaitingAck`, `closedOwners`; the sqlite store's `owner_messages` and `owner_tombstones`), which keep every unresolved message regardless of age with its coverage, revisions and deletion state. An owner `INBOUND` (or edit) in the event history with neither a row nor a tombstone, as after a tracking reset, gets a `quarantined` row: the lead gets one digest-priority `OWNER_QUARANTINED <count> <channel>:<id>,<id> ...` listing all of them once, and they are never reminded, never posted to the owner as delayed and never handed to a new lead. `dori ack`, a new edit or a delete turns a quarantined message into an ordinary tracked one.

**Handling.** An acked owner message stays tracked until `dori handled` covers its task count (default 1). After `handledTimeoutMin` without full coverage the lead gets urgent `UNHANDLED <channel> <messageId> coverage=<linked>/<tasks> <original event>`; the body is redacted and cut to 2000 characters. Another window later the owner gets `unhandledNotice` once. Unfinished owner messages are never dropped and join every cold-restart handoff. Taking an event only advances delivery, it doesn't finish the owner's work: an owner message taken but not handled stays an `UNFINISHED` reminder on every take until `dori handled` covers it, with no cold restart needed, and an `UNHANDLED` reminder you took keeps pushing and escalating while the work stays overdue. `dori ack` only starts the handling window.

**Lane outcome reports.** A claimed or finished lane must be reported to the owner by the lead, the only voice to the owner; taking its event is not reporting it. The first live `LANE_DONE_CLAIMED <key>`, `LANE_CLOSED <key>` or `CI_MERGED ... lane=<key>` that reaches the lead (a lead class in `eventPolicy`) opens one report obligation for that lane in the journal (`outcomes`; sqlite `lead_state.outcomes`, schema 5); later outcome events of the same lane join it, so a claim, its `CI_MERGED` and its `LANE_CLOSED` are one report, and reporting at the claim covers the close. That matters because the seen-claim close is digest and wakes no one: the claim is when the lead reports. A rejected claim (the supervisor's `LANE_NOT_DONE <key>` or the lead's `dori object-done <key>`) drops the obligation that claim opened, even if already reported, so the next claim or close opens a fresh one. `LANE_AUTO_CLAIMED` and `autoClose: machine` lanes open nothing. Outcome events found only in the history at startup open nothing. `dori reported <key> --text TEXT` posts the report and closes it (a receipt for a lane with no obligation yet is kept, so its outcome event opens nothing); reported rows are kept 7 days for that dedupe. While an obligation is open past `reportTimeoutMin` the lead gets urgent `UNREPORTED <key> finished <N> min ago and the owner has not been told: run dori reported <key> --text TEXT to post the outcome to the owner in its thread. <first outcome line>`, re-sent with backoff (see `reportTimeoutMin`) and never while a lead restart runs. The first `UNREPORTED` fires earlier, right after the lead's turn that received the outcome ends with no report receipt (the lead seen working after delivery, then idle or done); `reportTimeoutMin` still covers leads not observed. A lane whose brief declared `autoClose: machine` owes nothing. Open obligations join every cold-restart handoff as `UNREPORTED <key> <first outcome line>` lines, are published to `<stateDir>/unreported.json` for `dori inbox take`, and show in `dori status` (`unreported N`). The supervisor never posts the report or any notice about it to the owner; its lane finish line (below) is not a report and closes no obligation.

**Take receipts.** `dori inbox take` (below) is the lead's read path. Its receipts in `<stateDir>/takes/` move the take cursor (`Journal.inbox.takenOffset`, always a line end) forward only: the supervisor persists the cursor, writes `<stateDir>/inbox-cursor.json` (tmp, fsync, rename, directory fsync) and only then drops the receipts, so the next take never reprints. A first start puts the cursor at the log's end; entering push from a journal written under the old `tail` mode, or turning `tailMonitor` off, moves it to the end again (`INBOX_CURSOR_ADVANCED`), and a cursor past the log's end is reset to it (`INBOX_CURSOR_RESET`). A restart never moves it.

**Push delivery.** Appending to the log stays as above. After every delivery pass (every 5 s, so a burst becomes one push within 5-10 s), events past the take cursor that the lead has not taken are checked. An owner message or edit enqueued before its ack or handled time counts as taken, so do compacted or tombstoned ids; an `INBOUND_DELETE` of a message the lead acked does not. When an urgent one is untaken, or a digest one is `digestMaxDelayMin` old (`*_WARN` never alone), an idle lead gets one line typed into its pane, `[dori] supervisor: N new events (urgent: KIND x2, ...). Not an owner message. Run dori inbox take, then continue your task.` (`LEAD_PUSH <batch> <n> <kinds> <delivered|unconfirmed|failed> attempt=<k>`). The push is journaled before it is sent. Only an empty input line is typed into: other text is left alone (`LEAD_PUSH_INPUT_BUSY`), and a line still holding our own pointer, or a lone `[paste #N]` placeholder, gets one more Enter (`LEAD_PUSH_ENTER_RETRY`), also checked `pasteCheckMs` after a push that did not visibly start a turn. A paused session gets `/resume` first. A blocked or unclassified lead is never pushed to, and a working one only with `toWorking` (default true): after `ackSec`, and only into an empty input box, never over owner text; set it `false` to wait for idle again. The pointer also lists `; lanes: <keys>` (cut to `+N more`). One push is outstanding at a time: untaken after `ackSec` it is pushed again, after `retries` more pushes with doubling intervals up to 10 min (`LEAD_PUSH_UNTAKEN` once). Nothing makes a herdr call while nothing untaken is due.

**Escalation and the restart cap.** An idle lead is cold-restarted (`LEAD_PUSH_ESCALATE`, `force`) when, with `tailMonitor` on, an owner message stays readable and unacked for `escalateMin`, or, with it off, an urgent event stays untaken for `escalateMin` counted from the latest of its enqueue time, the lead's start and the first push attempt, so a new lead always gets a pointer first. Working leads are left to `stuckRestart`: its one-tool-call rule runs on `escalateMin`, and its idle rule is off. An unreported lane outcome (Lane outcome reports, above) past `reportTimeoutMin` counts like an untaken urgent event whether or not its events were taken: it keeps the lead pushed (`UNREPORTED` in the pointer) and, with `tailMonitor` off, escalates an idle lead `escalateMin` after the latest of its due time, the lead's start and the first pointer that carried it. Unacked owner messages are re-pushed, never enqueued as a separate event (the owner notice still is). A working lead with an identified process but no resolvable session file is judged stuck on `push.escalateMin`. Forced restarts are journaled for an hour (`forcedRestarts`, recorded once the lead really stopped); past `restartMaxPerHour` the push ladder refuses the unread-driven restarts (`stuckRestart`, the ladder), logs `LEAD_RESTART_CAPPED` and tells the owner once per hour, journals urgent `LEAD_UNRESPONSIVE <what>: ...` once per hour (alone it never cold-starts the lead), and keeps pushing. Cold starts for a missing or over-context lead still run. The new lead's prompt starts with `dori inbox take` and lists only unfinished owner messages and held launches; the tail command is added only with `tailMonitor`.

### `dori memory check`
Read-only check of the lead's memory (`memoryCheck`); it never writes the memory repo. Prints `MEMORY_FILE`, `SIZE <bytes> (<KB>), limit <KB>: ok|OVER by <KB>`, `OPEN_ITEMS <n>`, one `STALE #<n> "<item start>": <refs>` per Open item (a top-level bullet under `## Open`, with its indented lines) that names finished work, `UNCHECKED <ref>: <why>` for references it could not verify, and a last `MEMORY_CHECK action needed|clean` line. Finished work: a closed lane (a lane in `<stateDir>/lanes-archive/`, or a file hand-moved to the old `<stateDir>/lanes-closed`, now `lanes-archive/legacy/`, whole-word key match, never a key that is open again) or a merged PR (`owner/repo#N`, a github.com pull URL, or `PR #N` when the item names exactly one repo as `owner/repo` that is watched, named in a lane's Done signal, or under one of their owners; checked with `gh pr view`). Exit 0 when clean, 1 when `human.md` is over the limit or an item is STALE, 2 when it cannot check (memory not found, bad usage).

Under `dori supervise` the `memory` sweep runs the same check once every 24 hours and 15 minutes after a newly closed lane is first seen (so the lead's own cleanup turn comes first). Findings become one digest `MEMORY_CHECK <findings> (run dori memory check, then condense or delete them)` line for the lead, sent again only when the findings change; a missing memory repo is `MEMORY_CHECK_WARN <reason>`, retried on the next turn. State: `<stateDir>/memory-check.json`.

### `dori inbox take [--max-bytes N] [--peek]`
Lead-only (`LANE_PERMISSION_DENIED` in a lane). Prints the delivered events past the take cursor, `max(<stateDir>/inbox-cursor.json, every unconsumed receipt)`, one `<id><TAB><line>` per event, whole lines only and at most `N` bytes (default `delivery.push.takeMaxBytes`, 16384; a single longer line is printed alone). A line still being written is never printed. When more lines wait it ends with `INBOX_MORE <lines> <bytes>`: handle what it printed, then run it again. Nothing new prints `INBOX_EMPTY`. Each take that printed something writes an immutable receipt `<stateDir>/takes/<ms>-<uuid>.json` (`offset` = the end of the last printed line, `ids`, `at`, `session`); `--peek` writes none. Before the supervisor has published the cursor it refuses with `INBOX_UNAVAILABLE` (exit 2) instead of printing the whole log.

Before the closing `INBOX_MORE` or `INBOX_EMPTY`, what the last cold start carried over is listed first: `unfinished:<eventId><TAB>UNFINISHED <eventId> ...: <original line>` for each owner message the previous lead took but did not handle (until `dori handled` covers it, or the owner edits or deletes it), and `launch-queue:<session><TAB>LAUNCH_QUEUE ...` while held launches wait (`<stateDir>/carried.json`, pruned by the supervisor). Then every claimed or finished lane still not reported to the owner is listed as `unreported:<key><TAB>UNREPORTED <key> since <ISO time>: run dori reported <key> --text TEXT to post the outcome to the owner in its thread`, on every take (also with `--peek`). When the batch holds both owner messages (`INBOUND`, `VISITOR`) and lane outcomes or `UNREPORTED` reminders, the first line is `checklist:<first id><TAB>CHECKLIST this batch owes: reply to <n> owner message(s); report lane <k1>, <k2> (dori reported <key> --text ...)`; with only one kind there is none. The order is owner messages, edits and visitor lines first (under `## owner` when lane groups are shown), then the lane groups, then `## other`. The CHECKLIST line counts distinct owner messages, edits and carried unfinished-owner notices included.

### `dori reported <key> --text TEXT [--final] [--to TARGET] [--thread ID] [--note TEXT]`

Lead-only (`LANE_PERMISSION_DENIED` in a lane). The rule: run this to report a claimed or finished lane's outcome to the owner; it posts `--text` itself (target `--to`, else the lane's bound thread; a lane with no thread needs `--to`) through the same clients as `dori send`, and a bare `dori reported <key>` is refused with the usage line. It writes an immutable receipt `<stateDir>/reported/<ms>-<uuid>.json` (`lane`, `at`, optional `note`, `message`, `target`, tmp, fsync, rename, directory fsync) that the supervisor consumes on its next delivery pass (`LANE_OUTCOME_REPORTED <key>` in its log), which closes the lane's report obligation and stops `UNREPORTED`. The key must be a registered lane, open or archived. The receipt is written only after the post returns a message id; a failed post exits 1 with no receipt. Prints `REPORTED_RECORDED <key> <messageId>`.

A report posts without a close button unless it is `--final`; `dori supervise` posts the button itself (see below), so `--final` is optional. A `--final` report posted into a thread (the lane's bound thread, a `discord:<channel>/<thread>` or `discord:<thread>` ref, a bare thread id, or `--thread`; an id listed in `discordChannels` is a channel, not a thread) carries the button only when nothing is left on that thread: the reported lane is `done-claimed`, `verified-done` or closed, no other open lane is bound to the thread, no wait is registered with that thread (`dori wait --thread`), and no open decision obligation (`unresolved.json`) names one of those lanes. Otherwise the report still posts and records its receipt, without the button, and prints `REPORT_BUTTON_WITHHELD <key>: <reasons>` (`; `-separated); the supervisor posts the button once they clear. A `--final` report is withheld the button too when the supervisor already posted one into that thread after the reported lane closed (`the close button is already posted on this thread`). Use `--final` only for the report that ends the thread's work, never for an interim one.

Every receipt records the lane's thread (the thread that got a `--final` button, else the lane's bound thread, else the thread the report went into) and whether it carried the button. On each delivery pass `dori supervise` posts the close button, as a `[System]` message, into a thread that had a report recorded after its last close button, once every lane bound to that thread is closed, every finished lane on it is reported, no wait is registered with it and no decision for its lanes is open; so it lands right after the last lane closes or right after the last report, whichever comes later. It logs `CLOSE_BUTTON_POSTED <thread>` (a failed post logs `CLOSE_BUTTON_FAILED <thread>: <error>` and is retried on the next pass with the same nonce). Threads that got a button, from a `--final` receipt or from the supervisor, are kept in `close-buttons.json` (thread id -> time), so a thread gets one button per report and never a second for the same work. Older receipts without a thread post no button. The **스레드 닫기** button's `custom_id` (`dori:close-thread:<thread>`) holds the thread id, so it works after any restart. `dori supervise` handles the click on its gateway without the lead: a non-owner gets an ephemeral refusal; the owner's click updates the message (button disabled, labelled 닫았습니다), archives the thread and enqueues digest `THREAD_CLOSED_BY_OWNER <thread> [lane <key>]`. A failed archive re-enables the button. A repeat report of a lane into the same thread without a button keeps that lane's last report time, so it does not re-arm the thread's close button; receipts are taken in time order. New work in a thread uses a new lane key.

### `dori ack <channel> <messageId> [--tasks N]`
The lead's read receipt on a Discord owner message: removes the bot's hourglass (a missing one is fine), adds the eyes, then writes `<stateDir>/acks/<channel>-<messageId>.json` for the supervisor to consume. The ack is recorded only after the eyes are on the message, so a failed reaction exits non-zero and leaves the message to be reminded. Ids are the two numbers in the `INBOUND` line (for a thread message, the thread id is the channel). Once the ack is recorded it also sends the Discord typing indicator to that channel, which Discord shows for about 10 seconds or until the bot posts there, so it covers the gap to the short reply. The lead runs `dori ack` in a call of its own, then `dori inbox take` once more, so follow-ups in the same channel (new messages, edits, deletes) are merged into that one reply before any work starts. That step is best effort: a failure prints `ACK_TYPING_FAILED <channel> <messageId>: <error>` on stderr and the ack still succeeds. After every pair is acked, it previews the owner events still unread in each acked channel (once per channel, in the order acked): `UNREAD <channel> <INBOUND|INBOUND_EDIT|INBOUND_DELETE> <eventId> <preview>` per event past the take cursor, at most 5 per channel and then `UNREAD_MORE <channel> <n>`, or `UNREAD_NONE <channel>`. Only the acked messages themselves are left out; their edits and deletes are listed. The preview is read only: it writes no take receipt and moves no cursor, so the next `dori inbox take` prints the same events in full, and it is a hint, not a replacement for that take. When the cursor is not published or the log cannot be read it prints `UNREAD_UNAVAILABLE <reason>` and the ack still exits 0. Uses `DORI_DISCORD_TOKEN`. `--tasks N` declares how many separate tasks the message holds (see `handled`).

### `dori handled <channel> <messageId> [--tasks N] [--lane KEY ...] [--reply] [--all] [--reply-id ID] [--task-id ID]`
Declares what covers an owner message: each distinct `--lane` (it must exist in the registry) covers one task, and `--reply` covers one more. At least one of `--lane`, `--reply` or `--all` is required. `--all` declares every task of the message covered (one reply that answers a multi-task message): the task count settles on the linked coverage, counting the reply when no lane is linked, so UNHANDLED and `UNFINISHED` reminders stop. `--tasks N` sets the task count for a message with several requests, such as work in several projects; it defaults to 1 and only grows. Prints `HANDLED_LINKED <channel> <messageId>`, which means the link was recorded, not that every task is covered. Coverage is your declaration, not proof the lane finished. It changes no reactions.

### `dori recover [key]`

Runs the supervisor's lane recovery immediately, for one key or all working lanes. A missing pane is recreated using its recorded brief, cwd, model and mode. A restored `omo` without `--model`, or with a model different from the registry, is also replaced on the recorded model before freshness can nudge it. Matching live panes and paused or closed lanes are left alone. Recovery attempts are bounded and persisted in the registry; each successful recovery posts one explanation in the lane's thread. A lane with a recorded session is relaunched on that session (`LANE_RECOVERED ... session-resumed`), else from its brief. If the lane's provider or the Claude gate is blocked, nothing is launched and urgent `LANE_RECOVERY_BLOCKED <key> <pane> ...; not relaunched` is sent once per reason. After the last attempt fails, urgent `LANE_RECOVERY_EXHAUSTED <key> <pane> ...` is sent once; `dori status` marks the lane `[recovery gave up]` and `dori doctor` fails its `lane recovery` check.

### `dori lead-restart [--model ID] [--thinking LEVEL]`

Records a durable cold-start request in `lead-restart.json`. The next idle supervisor delivery honors it even without traffic and below both context caps; a working, blocked or unknown lead is never interrupted, and an idle one still waiting on its own children only after they finish or `leadChildWaitMaxMin` passes. The request captures the current configured model, so editing `leadModel` then running `dori lead-restart` takes effect without restarting the supervisor. Overrides apply only to the lead. `status` and `doctor` show the pending request until startup confirms; a newer request arriving during startup stays pending. A missing lead pane is recreated by the supervisor before the request runs.

### `dori update [--dev] [--force]`

Lead-only (`LANE_PERMISSION_DENIED` in a lane). Updates the git checkout the running `dori` comes from (found from the script's location, not a fixed path) to `origin/main`, or `origin/dev` with `--dev`. It runs `git fetch`; when the checkout is on another branch it checks out the target and prints `BRANCH_SWITCH <from> -> <to>`. Uncommitted changes to tracked files are stashed before and popped after. If the pop conflicts it stops with `UPDATE_STASH_CONFLICT`, keeps the stash, leaves the supervisor alone and exits 1. Only fast-forwards: a branch with local commits stops with `UPDATE_NOT_FAST_FORWARD`, puts back the branch and local changes it started with, and exits 1. When `package.json` or `bun.lock` changed, it runs `bun install --frozen-lockfile` (`DEPENDENCIES_INSTALLED`). When HEAD moved, or with `--force`, it restarts `dori-supervisor.service` and waits for it to leave `activating`. Before that restart it refreshes the guard agents (below), so the restarted supervisor sees the new agents and raises no OUTDATED for them. It prints `UPDATED <branch> <old>..<new> supervisor=<state>` and exits 1 unless the state is `active`. With nothing new it prints `UP_TO_DATE <branch> <sha>` and restarts nothing. Any failed git step prints `UPDATE_FAILED ...` and exits 1.

On both the `UP_TO_DATE` and `UPDATED` paths it also checks the guard agent on every guard machine (see `dori guard`): a machine whose `~/.dori/guard-agent.version` differs from the template's version gets it re-installed. Only a version probe that exits 1 or prints nothing counts as no agent and triggers an install. An unreachable machine (probe timed out or ssh exit 255) logs `GUARD_AGENT_UNREACHABLE <label> <detail>` and is skipped. A Windows worker's version lives in `%USERPROFILE%\.dori\guard-agent.version` and is compared with the PowerShell template's version. A machine with neither POSIX sh nor PowerShell logs `GUARD_AGENT_SKIPPED <label> <detail>` and isn't counted as failed; any other probe exit code logs `GUARD_AGENT_FAILED <label> version probe failed (exit N): ...` and is skipped. Otherwise it logs `GUARD_AGENT_CURRENT <label> <v>`, `GUARD_AGENT_UPDATED <label> <old|none>..<new>` or `GUARD_AGENT_FAILED <label> <detail>` per machine, in completion order. Skipped and failed machines are only logged and never change the exit code. Nothing is checked after an `UPDATE_*` failure.

### `dori wait <key> --until SIGNAL --note TEXT [--thread REF] [--every SEC] [--timeout MIN]`
Registers a durable follow-up for `dori supervise`; give `--thread` the thread of the work it follows, so the close button (the supervisor's, or a `dori reported --final` one) waits while it is registered. It uses the same signal syntax as `Done =` (`merged`, `closed`, `published`, `command`, `file`, `url`). Checks default to every 60 seconds with a 10-second bound; relative file paths and commands use the registration directory. `--timeout` is an optional deadline in minutes. Completion emits urgent `WAIT_DONE <key> <note>`; expiry emits `WAIT_TIMEOUT <key> <note>`, with `thread=REF` when supplied. The wait is then removed. State in `waits.json` survives lead, supervisor and machine restarts; keep it with the supervisor inbox and event log for deduplication. A failed check leaves the wait registered. A check that throws or times out counts as a failure; a wait with no `--timeout` that fails `waitMaxFailures` times in a row (default 30) ends with urgent `WAIT_FAILED <key> <note> (...)`. A `waits.json` that won't parse is moved to `waits.json.corrupt-<ms>` and reported once as urgent `WAITS_CORRUPT`; every wait in it has to be registered again.

`dori wait --list` prints JSON. `dori wait --cancel <key>` removes a wait; cancel before reusing an existing key.

### `dori emit <KIND> --text T [--id ID]`
Spools one event `<KIND> <T>` in `<stateDir>/emit/` for the supervisor's `emit` source. Its class comes from `eventPolicy` like any other kind (unknown kinds get `eventPolicy.default`). With `--id` a repeat of the same id is dropped by the journal's dedupe; without it every call is its own event. `KIND` is uppercase letters, digits and underscores, and may not be a built-in kind (`INBOUND`, `LANE_*`, `WAIT_*`, `GH_PR`, `SOURCE_FAILED`, ...), so no source can pass itself off as the owner or a lane. Prints `EMIT_QUEUED emit:<id>`.

### `dori source list [--json]` / `dori source add <name> --type poll|webhook|file ...` / `dori source remove <name>`
Lead-only. Manages `<stateDir>/sources.json` (mode 0600; the supervisor rereads it every polling pass, so no restart and no code change). `list` shows every source, built-ins first, with its events, dropped duplicates, last event kind and time, and its error while failing; a webhook secret is never printed. Kinds follow the `dori emit` rules.

- `--type poll --command CMD --every SEC --match RE --kind KIND [--cwd DIR]`: runs `CMD` (a shell line run with `sh -c`, or a JSON argv array) every `SEC` seconds (at least 5, killed after 30 s). Each stdout line matching `RE` is one event `<KIND> <line>`, deduped by the first capture group of `RE` when it has one, else by the whole line, so a poll runs for ever and reports each match once. Without a capture group, repeats of the same line text collapse into one event; capture an occurrence id when each repeat matters. `dori source list` flags such a source with an `identity` note (an `identity` field with `--json`). A non-zero exit is a failure of this source only.
- `--type webhook --port P --kind KIND [--secret S]`: listens on `127.0.0.1:P` only. A `POST` carrying `X-Dori-Secret: S` (or GitHub's `X-Hub-Signature-256` HMAC of the body) is one event: the JSON body's `text` (else the raw body, up to 64 KB), deduped by the body's `id`, an `X-Dori-Id` or `X-GitHub-Delivery` header, else the body's hash. It answers `202 {"ok":true,"duplicate":false}` only after the event is journaled, `401` for a wrong or missing secret (counted as `rejected`), `405` for other methods. Without `--secret` one is generated and printed once. To receive from outside the machine, put a separate tunnel in front of it; never route it through the owner's remote-access cloudflared.
- `--type file --path FILE --match RE --kind KIND`: tails `FILE` from its end at first sight (no history flood); each new complete line matching `RE` is one event. The read position survives restarts in `sources-status.json`, and a truncated or rotated file is read again from the start.

### `dori schedule add <name> ...` / `dori schedule list [--json]` / `dori schedule remove <name>` / `dori schedule run-now <name>`
Lead-only. Scheduled jobs: `schedule` sources in `<stateDir>/sources.json`, run by the supervisor's polling pass. Kinds follow the `dori emit` rules.

- `add <name> (--cron EXPR | --every SEC) (--text T | --command CMD [--cwd DIR] [--heavy] [--timeout SEC]) --kind KIND [--tz ZONE] [--catch-up once|skip]`. `--cron` takes 5 fields (minute hour day-of-month month day-of-week: `*`, `N`, `N-M`, lists and `/STEP`; with both day fields restricted either one matching fires, as in cron) or `@hourly`, `@daily`, `@weekly`, `@monthly`, read in `ZONE` (default `Asia/Seoul`). `--every` is at least 60 seconds, counted from when the job was added. No slot before the job was added ever runs. A `--text` job journals `<KIND> <T>`. A `--command` job (a shell line run with `sh -c`, or a JSON argv array; killed after `--timeout`, default 600, at most 3600 seconds) journals `<KIND> <name>: <output>` on exit 0 and `SCHEDULE_FAILED <name> exited <code>: <output>` otherwise (digest unless `eventPolicy` says else); a failed run is reported, not retried. `--heavy` runs the command only in a free heavy slot (`heavySlots`, `heavyMaxLoad`, the same slots as `dori heavy`): a due heavy job waits, pass by pass, without blocking the other sources, and keeps its slot until it finishes. Prints the job and `SCHEDULE_ADDED <name> next <time> KST`.
- Each slot is one operation row, recorded before it runs and never planned twice, so a supervisor restart never repeats a run. A slot found more than 5 minutes late, or several slots passed while the supervisor was down, follows `--catch-up`: `once` (default) runs the newest missed slot once, `skip` records it as skipped. A crash while a command ran leaves the row `attempted`: on the next start the journal decides. The result is there: verified. A `--text` job without it emits again (the event id dedupes it). A `--command` job without it becomes `ambiguous` with one urgent `OPERATION_AMBIGUOUS <id> ...`, and the command does not run again until `dori ops resolve <id> --as verified|retry`.
- `list` shows each job with its schedule, next run, last run and result; `remove` deletes it (its rows stay in the store); `run-now` queues one run in `<stateDir>/schedule-now/` that the supervisor runs on its next pass as its own row (`now@<time>`), leaving the schedule as it was.

### `dori watch`
Runs forever. Every 30 seconds it prints each new claim once (`LANE_DONE_CLAIMED`). Claims older than `closeAfterMin` are settled: unpushed or uncommitted work and failing signals turn into objections (`LANE_NOT_DONE`); otherwise the lane is closed (`LANE_CLOSED`). The deadline lives in the registry, so a restart picks up where it left off. The window starts at delivery to the lead, and an `autoClose: machine` lane prints `LANE_AUTO_CLAIMED` and `LANE_AUTO_CLOSED` (see Claim delivery under Always-on behavior). One lane's error prints `LANE_WATCH_WARN <key> <reason>` and the other lanes are still watched.

For a remote lane (working or not-done) it reads the newest `[REPORT]` line in its pane. A new `done` report becomes the claim the lane cannot make itself (`dori claim-done` with that evidence: same window, same live re-check, remote worktree checks skipped); a new `blocker` or `question` prints urgent `LANE_REPORT <key> <kind> <text>`. Each distinct line is acted on once, so an objection tells a remote lane to print a done line with updated evidence, and its footer says the same. Lines whose text starts with `<` are the footer's placeholders and are ignored.

Cleanup sweep: for a closed lane whose close receipt lists a worktree as kept (it could not be removed then, typically untracked files), the watcher removes it once `git status --porcelain` is clean, only under `worktreeRoot`, and prints `WORKTREE_CLEANED <key> <paths>`; a failed removal is a `LANE_WATCH_WARN`. Open lanes (working, not-done, paused, done-claimed) are never touched, whatever their PRs say.

### `dori freshness [--loop MIN]`
For lanes that have gone quiet: after `nudgeAfterMin`, a lane herdr reports as `working` is never nudged. Its pane is read (no model turn) and the in-progress todo item is posted to its thread through `progressTemplate`, scrubbed: at once when the item changes, and again every `nudgeAfterMin` while it does not. A post counts only when the hook exits 0; otherwise it is retried on the next tick and `PROGRESS-FAILED` is printed once per distinct error. When nothing can be posted (no Todo item on the pane, or no `threadReply` hook) it prints urgent `NO-PROGRESS` once per silence. Only an idle silent lane gets the pane nudge, once per silence. It gives three ways out, each in the lane's own report form: claim done when the deliverable is done (`dori report <key> done`, `dori claim-done` on the older footer, a `done` line for a remote lane), report a blocker outside the lane (`dori report <key> blocked`, a `blocker` line otherwise), or post a progress line and keep working. One still idle and silent `idleEscalateMin` after it is not nudged again: the lead gets urgent `IDLE-ESCALATE <key> ...` instead, then again after twice the previous wait each time (30, 60, 120 min with the default) until the lane updates its thread; its next silence starts over with a nudge. A working lane's `NO-PROGRESS` never escalates this way. Then the lane's last `[REPORT]` line posted to its thread after `postAfterMin`, with home paths and pane ids scrubbed. The nudge, `NO-PROGRESS` and the report post each happen once per silence; only the todo post repeats. The line is posted only once it is still the last `[REPORT]` line on the next tick (`PENDING-REPORT` the first time) and differs from the line posted last time (`STALE-REPORT` otherwise). A held-back outcome is printed once per change, not on every tick. A nudge reports its delivery as `delivered` (the agent status moved to working) or `unconfirmed`. A nudge that could not be typed (the lane's input line holds other text, or the pane is not live) or stayed unsubmitted in the input line is not counted as sent: it is retried on every tick, and `NUDGED ... delivery failed` is printed once per silence.

A lane's `dori report` rows are its progress (the router posts them): a working lane with a row newer than `nudgeAfterMin` costs the freshness sweep no herdr call. Its pane is read as above only once no row arrived within `nudgeAfterMin`, and its silence counts from its newest row or reply. Lanes that never write rows keep the screen-based progress and nudge.

### `dori dead-panes [--loop MIN]`
Prints `DEAD_PANE <id>` once per hour for a pane with no running agent status whose last lines match `deadPanePatterns` on two ticks in a row with the same text. A pane herdr reports as idle, working, blocked or done is never dead. A pane that is neither is unrecognised; three unrecognised ticks in a row print `UNRECOGNISED_PANE <id> ...` once (list non-agent panes in `ignorePanes`). A dead lane pane also adds one `blocked` report row, so the lead gets urgent `LANE_REPORT <key> blocked pane <p> stopped ...`.

### `dori guard [--loop MIN]`
Prints `HOST_GUARD ALERT <reasons>` when load, free memory, free disk or the pane count crosses its threshold, and `HOST_GUARD CLEAR` when it recovers. An ALERT ends with `; lanes by memory: <key> <total> (<command> <size>, ...), ...`: the three heaviest lanes by resident memory, each with its heaviest commands. A process belongs to the lane its own `DORI_LANE_KEY` names, else to its nearest ancestor's, so an emulator, expo or tsserver a lane started counts for it (Linux only for now: the key is read from `/proc/<pid>/environ`). Under `dori supervise`, when free memory is below `memFreeMinPct`, the supervisor also types a `[System] HOST_GUARD memory warning` (what it uses, what to stop) into the pane of the heaviest lane overall, and the ALERT ends with `; warned <key> in its pane <pane>`, so the lead only has to read it. Nothing is typed, and the ALERT says why, when that lane isn't an open local lane with a pane (`not typed: heaviest lane <key> is not open here`; a lighter lane is never told instead), uses under 1 GB (`not typed: heaviest lane <key> is below 1.0 GB`), was warned in the last 30 minutes (`not typed: <key> was warned <n> min ago`), or sits on a question prompt. Low memory latches: it starts below `memFreeMinPct` and clears only once free memory is 2 points above it, so memory hovering at the threshold doesn't re-alert every minute. It also prints `COMPUTE_READY` / `COMPUTE_BUSY` as load crosses `loadOk`. Only changes are printed. Under `dori supervise` it also prints urgent `LAUNCH_READY` once when `dori can-launch` (or a held `launch`) last answered HOLD and the host now passes the same check so held work is started without waiting for anything else. The line ends with the queue: `; queued launches (N): <key> cwd=.. repo=.. thread=.. machine=.. done="..." brief=<path> queued <iso>; ... (dori hold list)`.

Under `dori supervise` the `machine-guard` sweep covers each worker machine: every saved herdr machine (`herdr machine list --json`) plus `guardMachines`. It runs after the other sweeps, apart from `guard` (which samples only this host), so a slow worker never delays them and a failed host sample doesn't stop it; its own failures are `SWEEP_WARN machine-guard ...`. If `herdr machine list` fails or returns invalid JSON, it keeps the machines listed before, emits `SWEEP_WARN machine-guard herdr machine list failed: <detail>` and retries the list after 1 min instead of 10; `guardMachines` are still sampled when no list was ever read. No daemon runs there. The guard agent is a POSIX shell script that the supervisor runs over ssh (`BatchMode=yes`, `--` before the target, 20 s limit) each round: `sh ~/.dori/guard-agent.sh sample` prints one `DORI_GUARD_SAMPLE` line with load, free memory, free swap and free disk (macOS and Linux; a metric it can't read is -1 and never alerts). Lines carry the machine label (whitespace becomes `_`) and appear only on change:

- `HOST_GUARD ALERT machine=<label> <reasons>[; lanes on this machine: <key>, ...]` (the open lanes whose `machine` is that label or its herdr machine id; lane memory is read on this host only) / `HOST_GUARD CLEAR machine=<label> load <n>, memory free <n>%, disk free <n> GB, swap free <n.n> GB`
- `HOST_GUARD OFFLINE machine=<label> <detail>` (urgent; unreachable or bad sample) on the 2nd failed sample in a row; a single failure emits nothing
- `HOST_GUARD NOT_INSTALLED machine=<label> guard agent not installed; run dori guard install --machine <label>` (digest, even when `eventPolicy.default` is `lead-urgent`), once, when the machine answers but has no agent
- `HOST_GUARD UNSUPPORTED machine=<label> <detail>` (digest), once, when the worker has neither POSIX sh nor PowerShell; the sweep then retries that machine only every 30 min, it never holds lane placement, and a later good sample gives `HOST_GUARD ONLINE`
- `HOST_GUARD ONLINE machine=<label>` (digest) when an OFFLINE or NOT_INSTALLED machine answers again
- `HOST_GUARD OUTDATED machine=<label> have=<v> want=<v>; run dori update or dori guard install --machine <label>` (urgent), then `HOST_GUARD CURRENT machine=<label> <version>` (digest) once it runs the wanted version again

A machine whose sample failed waits out a backoff before the next one: 2 min, doubling with each failure in a row up to 30 min; one good sample resets it. Each machine's alert, offline, outdated and not-installed flags, failure count and next sample time live in `<stateDir>/machine-guard.json`, loaded at supervisor start and rewritten atomically (temp file plus rename) after each tick, so a restart doesn't re-report unchanged machines. A missing or corrupt file starts empty; deleting it makes every problem machine report once more.

The agent's version is the first 12 hex chars of the sha256 of `scripts/templates/guard-agent.sh`, computed on the server; the install writes it to `~/.dori/guard-agent.version` next to `~/.dori/guard-agent.sh`.

Each machine's shell is detected once over ssh: POSIX sh, or Windows cmd/PowerShell. A Windows worker gets the native PowerShell agent instead, `scripts/templates/guard-agent.ps1`, installed as `%USERPROFILE%\.dori\guard-agent.ps1` and run through `powershell -EncodedCommand`. It prints the same `DORI_GUARD_SAMPLE`, kill and heavy lines with `os=windows`; `load1` is the CPU load percent times the logical processor count / 100. Its version is the sha256 prefix of the `.ps1` template, so the two agents are versioned apart. Windows kill closes windowed processes (5 s to exit) and force-stops console ones. `dori guard install` and the `dori update` refresh write both to temp files in `~/.dori` and `mv -f` them into place, so a sample never reads a half-written script.

Memory pressure has two stages. ALERT (free memory below `memFreeMinPct`) is the warning above: the ALERT line plus the typed warning to the eligible heaviest local lane; on a worker machine it warns every open lane there, matching its label or herdr machine id. CRITICAL (free memory below `memFreeCritPct`, or free swap below `swapFreeCritPct` of a non-zero swap total; on macOS workers only free memory decides) makes the supervisor kill every process whose full command line contains a `heavyKill` substring and that belongs to an open lane on this host (on a worker machine: any process of the ssh user). The local stages run in `guard`; the worker stages run in `machine-guard` only for machines due to be sampled. If it killed nothing, it pauses the heaviest local lane (on a machine: the most recently opened lane there). Each entry into critical emits one lead-urgent line; relay it to the owner:

- `HOST_GUARD CRITICAL <reasons>; killed <lane> <comm> <size> (pid <n>), ...`
- `HOST_GUARD CRITICAL <reasons>; paused <lane>`
- `HOST_GUARD CRITICAL machine=<label> <reasons>; killed ...`

The guard agent has two more subcommands for this: `sh ~/.dori/guard-agent.sh kill PATTERN...` (TERM, 5 s, then KILL for the ssh user's processes matching a pattern; prints `DORI_GUARD_KILLED pid=<pid> rss_kb=<n> cmd=<name>` per process and `DORI_GUARD_KILL_DONE count=<n>`) and `sh ~/.dori/guard-agent.sh heavy <label> -- <command ...>` (the `dori heavy` slot for a remote lane: `DORI_HEAVY_SLOTS` slots, default 1, under `~/.dori/heavy`).

### `dori guard machines` / `dori guard install [--machine LABEL]`

`machines` samples every guard machine once and prints `GUARD_MACHINE <label> online version=<v> current|outdated load <n>, memory free <n>%, swap free <n.n> GB, disk free <n> GB`, or `GUARD_MACHINE <label> offline <detail>`. `install` is lead-only: it copies the template over ssh to all guard machines, or one, reads a sample back and prints `GUARD_AGENT_INSTALLED <label> <version>` or `GUARD_AGENT_INSTALL_FAILED <label> <detail>`. Install probes the remote shell first and copies `guard-agent.sh` or, on Windows, `guard-agent.ps1`; a machine with neither POSIX sh nor PowerShell prints `GUARD_AGENT_SKIPPED <label> <detail>` instead, which isn't a failure. Every ssh detail skips client notices (the `** WARNING: ... post-quantum` block, known-hosts and no-tty notes) and shows the real error line. It exits 1 on any failure or when no machines are listed; an unknown label exits with the known ones.

### `dori hold list` / `dori hold drop <key>`
`list` prints the launches waiting after a HOLD as JSON. `drop` removes one and prints `HOLD_DROPPED <key>`, or exits 1 when the key is not queued.

### `dori quota [--json]`
Reads Claude usage now (pi-quota, no session or model turn) and prints the 5h and 7d usage with the time left to each reset (pi-quota's format: `2d 6h`, `2d`, `3.5h`, `40m`) and the reset time (KST) for every Claude account, then pi-quota's own block. It shows usage only: nothing is gated on it. `--json` prints the same usage as JSON. Without a Claude account it says so.

### `dori can-launch [--machine M] [--cwd D] [--done "..."] [--all]`
Checks the machine a `dori launch` with the same flags would be placed on (no flags: `placement.defaultMachine`; no fallback is tried). Prints `CAN_LAUNCH` and exits 0 when it has room for another lane. Otherwise it prints `HOLD <reasons>` and exits 4. A remote machine's line names it: `CAN_LAUNCH machine=<label>` or `HOLD machine=<label> <reasons>`; an unlisted label holds with `unknown machine <label>; see dori guard machines`, an unreachable one with `machine <label> unreachable: <detail>`. `--all` checks local and every listed machine, prints one line each, and exits 0 only when all have room. The reasons come from the guard's memory, disk and pane-count thresholds. CPU load alone never holds a launch, because it moves too fast to plan around. A HOLD leaves `<stateDir>/launch-hold.json` behind (one blocked flag per machine, lowered by that machine's next `CAN_LAUNCH`, or by the supervisor when it sends `LAUNCH_READY`, or `LAUNCH_READY machine=<label>` for a remote machine, which lists only that machine's queued launches; queued launches stay), so run it when you are about to launch, not as a status probe: every HOLD answer is read as queued work.

### `dori send discord --to TARGET --text TEXT [--thread ID] [--edit ID | --buttons JSON]`
`--buttons` attaches one action row to the message's last chunk: a JSON array of 1-5 `{"label": ..., "id": ..., "style"?: "primary"|"secondary"|"success"|"danger"}` (default `secondary`, labels up to 80 characters, ids unique) whose ids match `^dori:hook:[a-z0-9-]{1,20}:[A-Za-z0-9._:-]{1,70}$` (see [Discord button hooks](#discord-button-hooks)). A malformed value exits 1 with the first problem on stderr and posts nothing; it cannot be combined with `--edit`.

Posts a message, or edits one with `--edit`. `--to` is a plain id or a lane thread ref (`platform:parent/thread`, as in `lane.thread`), so the default hooks can pass `{thread}` straight in: Discord posts to the thread id. An explicit `--thread` wins; on Discord, `--to <channel> --thread <thread>` posts in the thread. The token comes from `DORI_DISCORD_TOKEN`, read from the process environment first and then from `~/.dori/env` (the supervisor's EnvironmentFile), so a lead that did not inherit them still sends. A token missing from both exits non-zero with the error on stderr, which means the message was not delivered. Text containing `$(` is refused, since it can only come from a shell string. Rate limits are retried with the server's wait time; other errors fail at once.

Lead-only: inside a lane, `dori send` (and `--edit`) exits 1 with `LANE_PERMISSION_DENIED`, even to the lane's own thread. A lane asks with `dori report <key> question --text ...` and the lead relays the answer.

### `dori thread discord --to CHANNEL [--message ID] --name NAME`
Starts a Discord thread: on message `--message` when given, else a standalone public thread in `--to` (a channel id or `discord:<channel>` ref). Right after the thread exists, `discord.ownerId` is made a thread member, so the thread appears in the owner's thread list. When the owner is not a member yet it is added (`PUT /channels/{thread}/thread-members/{user}`) and `THREAD_OWNER_ADDED <thread>` is printed. When the starter message mentions the owner, Discord joins them as the thread starts, Discord shows no "added" line, and `THREAD_OWNER_ALREADY_MEMBER <thread>: ...` is printed instead. A failed add prints `THREAD_OWNER_FAILED <thread> <user>: <error>` after the thread ref and exits 1; an unset or non-numeric `discord.ownerId` prints `THREAD_OWNER_SKIPPED` and creates the thread without it. Prints `THREAD discord:<channel>/<thread>`, the ref to pass as `--thread` to `dori launch` and as `--to` to `dori send`. Lead-only; uses `DORI_DISCORD_TOKEN` like `dori send`.

### `dori typing discord <channel>`
`dori typing discord <channel>` sends the Discord typing indicator to a channel or thread. The target is a plain id or a lane thread ref, as with `dori send --to`. Discord shows it for about 10 seconds or until the next post there. There's no `--off` on Discord: it's rejected with the usage text. Lead-only. Uses `DORI_DISCORD_TOKEN`. Prints `TYPING discord <id> on`. `dori ack` on a Discord message sends it too.

### `dori presence discord`
Keeps the account shown as online until stopped.
- **Discord (non-supervised installs):** the bot connects to the gateway, identifies as online and handles `/quota` when `discord` is configured. Supervised installs use `dori supervise` for all three. The shared token-scoped machine/user lock refuses to start presence while a supervisor or another presence process owns that bot token.
- Run one instance per account. Two writers flip each other's presence.

### `dori transcribe <audio-file>`
Runs `hooks.transcribe` and prints the transcript. A failed or empty transcription is an error, never an empty message.

### `dori heavy <label> -- <command ...>`
Waits until load is under `heavyMaxLoad` and one of `heavySlots` is free, then runs the command and frees the slot when it exits. A slot held by a process that no longer exists (or a zombie) is taken over. Use it for full builds, test suites, emulators and simulators: one heavy job runs per machine at a time. Remote lanes use `sh ~/.dori/guard-agent.sh heavy <label> -- <command ...>`; a Windows remote lane's footer gives `powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\.dori\guard-agent.ps1" heavy <label> -- <command>`. Installs, focused tests and git do not need it.
